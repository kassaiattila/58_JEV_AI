# Architecture — the end-to-end process and the five planes

**Date:** 2026-09-27, reviewed 2026-09-30 · **Status:** describes the structure that actually works. The guarantees of section 6 apply to the path that runs through the worker; the command-line measurement paths are outside them.

**Plain-language summary.** The system is a general framework for processing documents and emails with AI. Each flow
reads a document or an email, lets code, JEV and OpenAI each make the decisions they are suited to, and stores the
result, together with its to-dos, in a local database. Three reference flows show how it works: document type
recognition, invoice data extraction and email intent. Documents and emails go into work packages, whose runs a
background worker processes, reserving the cost before every paid call; a local service and a browser interface give
access to all of this. This page describes the process end to end, the five planes the flows share and the layers built
on top of them.

**What this is:** a general, multilingual document- and email-processing **AI-flow framework**
(Burr + Pydantic + sidecar + JEV) in which the flows are instances and the framework layer (adapter, registry schema,
call-site schema, policy schema, eval, store, contract, input adapters) is shared. The process below shows the three
reference flows (M1 document type recognition, M2 Hungarian invoice with two paths, M3 email intent); a new flow sits on the same
planes. The reference flows are the yardstick for the efficiency and reliability of the framework and of the
JEV–Pydantic AI–Burr combination. Teachable document processing is a complementary goal: a versioned processing recipe
for a known type, general data-point proposals with source checking for an unknown one. The shared source- and
structure-checking capabilities serve both. OpenAI and JEV can both be used, for documents and emails alike; the division of labour between them is
decided per task by measurement (section 3).

**Package layout (208, plan G-process-core R2).** The code is in one folder per layer, lowest first:
`jav/core/` (the store, the settings, the registries, the decisions log, the call log and the job queue),
`jav/documents/` (reading, OCR and the native readers), `jav/ai/` (JEV, GPT, the candidates, the decision rules and the
type packs), `jav/flows/` (the Burr graphs and their registry), `jav/app/` (work packages, runs, results, outputs and
workflows), `jav/runtime/` (the worker), `jav/domains/<domain>/` (a domain's own modules), `jav/service/` (the local
service) and `jav/cli/` (the command line); beside them `jav/evals/` (measurement, with the three stand-alone tools of
section 13), `jav/devtools/` (the preflight, the guards, the generated documents) and `jav/legacy/` (the port of the
legacy project). A layer may import its own and the layers below it, never the ones above; a domain never imports
another domain; only the command line (and a domain's golden sets) imports the measurement. A domain's addresses of the
local service (`api_*`), its commands (`*_cli`) and its golden sets follow the rules of the service, the command line
and the measurement. `tests/test_dependency_direction.py` reads every module's imports, inside functions too: it fails
on a module outside the layers' folders and on a new import against the direction, and lists the ones that exist
today, each with the step that takes it away (the list can only shrink). A module that moved keeps a saved flow state
readable: the state persister reads its classes at their new place (`jav/flows/persistence.py` `MOVED_MODULES`). The
instructions and output schemas sent to the models are config data in `configs/prompts/` (209), not code. A domain's
tables are its own (209: the email tables left the shared store, `jav/domains/email/email_store.py`): a shared module or
another domain reaches them through the domain's registrations, and the same test fails on a module outside a domain
that names one of its tables in its SQL (the measurement and the developer tools excepted). The legacy project's
database is not a runtime dependency.

**Native document path.** Work packages also accept DOCX, XLSX, TXT and CSV. The worker dispatches these to
`jav/flows/flow_native.py`; the readers preserve structured source elements, and `jav/documents/native_results.py` stores immutable
readings and interpretation publications. Model calls use the existing provider adapters, receipts and budget ledger.
The API exposes complete source elements and source-linked facts to the native review views. Corrections retain the
original proposals, approval is bound to the displayed review version, and the shared result datasets include native
facts and reading status. PDF and email items keep their existing flows. A PDF whose recognised type has no fitting
type pack (a scan with the reader's local OCR) continues from detection into the native flow when the recipe's
`unknown_documents` setting is
`facts` (the default, 120); its result is then chosen by its native publication (`native_results.native_item`), not
by its suffix. The storage boundaries, failure states and
source-location contract are described in [Native document processing](guides/NATIVE_PROCESSING.md).

This page is written by hand. The generated parts are the graphs' `docs/flows/<flow>/FLOW.md` (in the repository), and
the JEV call-site catalogue and the state snapshot (local, generated from the store: `python -m jav.cli docs`,
`admin --write`). Rules: `CLAUDE.md` and the [development guide](guides/DEVELOPMENT.md); JEV capabilities:
`docs/JEV_PLAYBOOK.md`; security: `docs/SECURITY.md`; config files: `docs/guides/CONFIGS.md`.

Each PDF attachment is also an item of the email's work package and gets the full document processing
(M1 + M2, section 10). The email input can still be driven by hand: an old bridge started without `-RepoRoot` posts to
`python -m jav.cli email-ingest-server` and keeps its attachments under the legacy project's `data/inbox/email/<acct>/<eid>/`;
the receiver resolves both attachment roots (`jav/domains/email/ingest_server.py` `host_path`), and `email-inbox inbox/` then runs M3.

The **golden loop** is the same for every flow: golden set (referenced from the legacy project; the PII stays there) → run
with the cache ($0 thanks to the request hash) → report (`runs/*.jsonl` + Markdown) → discrepancy analysis from the raw
run → general rule (config change with a version bump) → rerun → determinism measurement without the cache. From live
data: a manual labelling list (`*_manual_sample.md`) → our own golden set (`golden_labels`). Situations the legacy sets do
not cover (credit notes, receipts without an invoice number; 151: the outgoing invoice) have invented cases in
`configs/golden_synthetic.json` (`golden --synthetic`), run and reported apart, so the legacy results stay comparable.
151: a local case list outside git (`golden --cases <file>`, `evals.load_case_file`) measures a path on real documents
against reference values, such as the other path's results; its run file is `<type>_local_<arm>` and its score is an
agreement, not an accuracy.
188: every golden set is in one registry (`jav/evals/goldens.py`) and one command measures them
(`python -m jav.cli measure [<golden set> ...]`, `--list` names them): the data points of each type pack with golden
cases on each of its paths (legacy and synthetic cases apart), the type recognition, the email intent, and the logic
packs' golden sets (the reconciliation's pairs and incoming money kinds, the quote's lines, matches and reply letters).
204: a logic pack's golden sets are described in its domain's measurement module (`jav/domains/finance/goldens.py`,
`jav/domains/quotes/goldens.py`), which the domain module names (`GOLDENS`) and the registry imports by name
(`goldens.logic_pack_goldens`), in the packs' registration order; until 204 the pack named them in its registration
(`LogicPack.goldens`), so its own module imported the measurement layer. A business module of a domain imports no
measurement code (`tests/test_golden_owners_204.py`).
Each set is measured by its own command's function with the same arguments, so the raw run files stay as they were;
without a budget only earlier answers count, and a paid round names one set. A round writes its sets' reports into
`runs/<stamp>_measure.log` and a receipt with the commit and one line per set into `runs/<stamp>_measure.jsonl`.
189: the coming quote request logic pack's golden set is invented (`configs/golden_quotes.json`, read and laid out
as mailbox folders by `jav/domains/quotes/invented_golden.py`); it joins the shared command when the logic pack registers it.
197: the packs converted from legacy types count with their flat expected records (the ticket's 11 cases, the general
terms' 10), and `facts:<family>` measures the general facts (the native path's source-bound facts, no type pack) on a
type pack's legacy golden documents with the pack withheld (`configs/golden_facts.json`, `jav/evals/evals_facts.py`): the
pack's scored fields are looked for among the facts by value, a repeated file is one document, and the documents are
split into a development and an evaluation half fixed before any measurement; the documents take the native graph's
reading and interpretation, are not published and open no to-do.
Teaching a type (197) starts from such a family: `python -m jav.cli type-propose <family>`
(`jav/evals/type_teaching.py`) reads the development half's measured facts (read only, no AI call) and proposes the names
that recur in at least three of its documents as fields, with their counts and a kind (a date when every value is
exactly one date); code joins only one name's spellings and a bilingual label's first part, never synonyms, and no
value is printed or kept (`--shapes`: the written forms of the development half's labels, letters and digits masked).
A person writes the draft (`configs/type_drafts/<key>.json`); `type-candidate <key>` makes its candidate pack the way
the legacy converter made the converted packs (pack, prompt, schema, a verification site that inherits `verify`),
never picked by detection, and lists the shared registries' entries still missing; `measure taught:<key>:evaluation` measures
the candidate on the family's evaluation half, on the G path (`taught:<key>:development`: on its own development half,
an in-sample check before the evaluation; a draft is corrected from that half only).
Detection picks a pack only by a person's command (199): `type-activate <key> [--replace <pack>]` and
`type-withdraw <key> [--restore]` turn the pack's own detection switch (`auto_detect`) as a new version with a
changelog line, and the files stay for the earlier results. A taught pack is turned on only with the latest shared
measurement of its evaluation half on a clean working tree, every case answered, on the files it has now (the legacy
activation gate); the result is shown and no threshold decides. `--replace` turns the family's pack it takes over off
in the same step, and `--restore` turns that one back on. A pack without detection anchors is turned on only as its
family's one pack, because next to another the anchor score would pick it without a question. The capability
catalog reads whether a type is active from the same switch.

## 3. Where each decision is made — the decision hierarchy in practice

1. **Code** (deterministic, tested): candidate finders, validators, body cleaning, anchor features, evidence matching,
   `next_flow`, the review latch. This is the mechanism.
2. **JEV** (judgement over a finite set of options): one of the tools for selection, presence and verification steps. One call site = one JSON config
   + one `build_state` + one `build_questions` + one `jev.ask(...)` through the adapter. Raw probability goes into the state,
   thresholds only into `policy.json`: a named band set per call site (`band_for`), Noul no / uncertain / yes,
   Choice auto / uncertain / human (confidence threshold + gap to the second option); the `uncertain` band triggers review only
   with `uncertain_review: true`. Because of the request-hash cache, the same (concrete model version, state, questions) gives the same answer
   for $0; since 200 the configured model is a concrete version (`configs/models.json` `jev.model`, `jev-1.14.0`), so
   the answers do not change by themselves; the provider's moving name (`jev.watch_alias`, `jev-latest`) is only resolved
   with a probe by the daily backup (`runs/cache/_model_versions.json`, 24 h TTL; `jav/ai/jev_version.py`), and the
   start-up check and the System page say when it points to a newer version (switching is a decision with a
   measurement). An alias still works as the model and is resolved the same way. If JEV still
   does not answer after the SDK retries, the adapter writes a ledger entry (`error`) and raises `JevUnavailableError`; the flows turn this
   into a `jev_unavailable:<reason>` review (M1/M3 `final_status = jev_unavailable`) instead of crashing. A request refused
   for the token limit (`max_tokens_exceeded`) is remembered under its key and the concrete version that refused it
   (`runs/cache/too_large/`, 200); it is refused again without a call, with the same reason, so the request-size frame
   (`jav/ai/jev_budget.py`) goes on to its tighter request at once and a free round can answer it. Processing without JEV
   is a guarantee (160, `jav/ai/engine.py`): a flow application built with `jev=False` runs every step inside `jev.disabled()`, so a
   JEV question asked anyway is refused before the model probe, the cache and the call log (`JevUnavailableError("disabled")`,
   the `jev_unavailable:disabled` to-do; `get_adapter()` refuses too, whatever adapter a run installed). In the tests the refusal
   fails the test (`tests/conftest.py`); a test of the refusal itself is marked `jev_refusal` (`tests/test_jev_safety_net_160.py`).
   The engine matrix (`configs/engine_matrix.json`, checked by `jav/devtools/engine_matrix.py` in the preflight) lists every JEV call
   site with its counterpart without JEV or a stated exception, and the tests that cover it; the paired tests
   (`tests/test_paired_*_160.py`) run each flow with both engines. Which engine a run uses: the application's AI engine
   (`app_settings.engine_default`, an `app_options` row; JEV and GPT unless someone changes it) is the default of every new
   processing setting that does not name one (`work_recipes.default_params`, `engine_params`): a package without saved settings, a
   mailbox download's package, a watched folder's package, an assignment without `jev`. Saved settings and started runs keep
   their own (a run freezes its settings when it starts); an assignment saved before the engine setting existed (recipes 1.9.0, 2026-10-02) has no `jev` and stays JEV and GPT.
3. **OpenAI, through Pydantic AI**: the existing G path and the general data proposal produce structured proposals and then apply source checking. The graphs described here neither restrict OpenAI to generating extracts nor make JEV the only tool for every interpretive decision: further interpreting, classifying and verifying roles are also permitted, for documents and emails alike. Any new division of labour must be built in on the basis of targeted measurement; source checking, separate cost accounting and manual activation apply to every role. The Burr states are plain Pydantic models, not Pydantic AI.
4. **OCR pipeline**: `jav/documents/ocr.py` + `configs/ocr.json` — PDF without text → page image (pypdfium2,
   300 dpi) → tesseract word boxes (native tesseract on the machine; the Hungarian + English language packs taken from the old sidecar's Docker image
   into `tools/tessdata`; fallback: the old sidecar image via `docker run`) → the same line/cell builder as for the text layer
   (`jav/documents/pdf.py: build_layout`). A separate graph step (`ocr_pdf`) in the M1 and M2 graphs, a disk cache in `runs/ocr/`,
   raw quality signals in the state, thresholds in the `ocr` block of `policy.json`. The rest of the old sidecar (torch, the matcher)
   has not been ported. When local OCR is weak, `ocr_with_escalation` asks Azure DI (paid): since 121 directly over its REST API
   (`jav/documents/azure_di.py`, standard-library HTTP, ported from the old sidecar's provider) when `AZURE_DI_ENDPOINT` and
   `AZURE_DI_KEY` are set, otherwise through the old sidecar, which sees only the legacy data folder. The call goes through the
   call log (`azure_recognise`): in a worker run the page count is reserved from the run's Azure budget (recipe switch
   `azure_ocr`); an analysis Azure accepted but whose result was lost is an uncertain call. A blocked or failed escalation leaves
   the local text and, unless the recipe switch is off, a to-do (`ocr:escalation_blocked:*`: budget, uncertain earlier attempt,
   no route to Azure, failed call). Since 123 the original Azure recognition (word polygons, page size, unit, angle)
   is kept once in the store, under the sha256 of its canonical JSON (`ocr.save_recognition`, artifact kind
   `azure_recognition`), and the digest travels with the recognition signals (`recognition_sha256`); the text, the
   OCR cache key and the call's request hash are unchanged. Since 124 detection names the recognition whose text
   went on (`ocr_recognition`; an Azure text cached before 123 has no kept original and names nothing), and a scan
   continuing into general facts takes it over in the native reader (`jav/documents/readers/external_recognition.py`, see
   `docs/guides/NATIVE_READERS.md`). Heavy dependencies may only go behind a sidecar.
5. **Isolated PDF reading**: `jav/documents/isolated_pdf.py` + `configs/service.json` `pdf_reader` — the third-party PDF parsers
   (pdfplumber for the text layer, PDFium for the OCR page images, the page sizes and the review page images) run in one
   long-lived helper process per calling process (worker, local service), one request at a time, with a time limit per
   request and a memory limit (on Windows a job object). Our own processing (words → lines and cells) stays in the
   calling process. Over a limit the helper is stopped and replaced; text extraction fails the item with a named error
   (`PdfReaderLimit`, no retry), the OCR page images give a to-do (`ocr:unavailable:PdfRenderLimit`), and a review page
   image is answered with 422. `isolated: false` runs the same functions in-process. 138: the same helper parses a
   tabular statement export (`statement_table.parse_rows`: openpyxl, defusedxml, the CSV reader) within the read time
   limit; a parser error keeps its message and a limit is a named refusal (`StatementTableError`, 422).

## 4. Tuning and changes — the procedure

| Change | Where | What follows |
|---|---|---|
| type or intent description (`what`), boundary (`not_for`), example (`examples`), family (`parent`) | `configs/doc_types.json` / `intents.json` (schema v2), bump `meta.version` + changelog | `detect-golden` / `email-golden` (new hash → live calls), `detect-determinism` / `email-determinism`; `eval-report` (parent-label section); regenerate `docs` |
| JEV instruction, Noul question | `configs/callsites/<callsite>.json` | the same; the local, generated call-site catalogue shows the statistics per version |
| band, threshold, route | `configs/policy.json` (`bands`, `band_for`, routes) | no rerun needed: `eval-report` shows from the raw runs (`runs/*.jsonl`) how many cases would change band |
| model, price, timeout, retry, cache version, alias TTL | `configs/models.json` | bumping `cache_version` invalidates every cache key; a model-version change (detected by the probe) produces a new key by itself |
| graph step | flow module + `CONTRACT` | `flows` lint + FLOW.md |
| code (regex, cleaner, validator) | `jav/<layer>/*.py` + test (TDD) | `pytest`, `recall`, golden |

Pitfalls: a `use_cache=False` run **updates** the cache file (it refreshes the reference), except for the determinism measurement,
which runs under `JevAdapter.no_cache_write()`: no reads and no writes, so the reference answer stays untouched.
The old inbox folders contain attachments only; any change to a Choice criterion means a new cache key. The cache
key contains the concrete model version (introduced with `cache_version` 2): even a fully cached golden run
needs one probe a day (an API key is required; offline, the resolution stored in the file is used, with a warning).

## 6. Execution layer: work package → run → worker

**Plain-language summary.** Documents go into a work package, the package gets its processing settings (or runs with
the default ones), and the run goes through a
durable job queue in the background. Before every paid call, an entry is written and the cost is reserved. After a stop,
the run resumes from the saved step, and a call that has already been paid for is not repeated. To-dos can be resolved
reason by reason, and a live run can only be approved when it has no open to-dos.

```mermaid
flowchart LR
  CLI[command line: wp-*, run-*, worker] --> WORK[jav/app/work.py<br/>work package, recipe, readiness, run]
  WORK --> Q[jav/core/queue.py<br/>job queue]
  W[jav/runtime/worker.py<br/>worker] --> Q
  W --> FLOW[Burr process<br/>flow / flow_detect + state persister]
  FLOW --> CALLS[jav/core/calls.py<br/>call log + budget]
  CALLS --> JEV[ai/jev.py]
  CALLS --> GPT[extract_llm.py]
  FLOW --> REV[store: review_reasons<br/>to-dos per reason]
```

## 7. Local service

**Plain-language summary.** The user interface and the command line use the same gateway: a service that can only be
reached from the local machine. It does not run anything itself; it only queues work and reads from the store. The
separate worker does the processing, so closing the browser or the service does not stop a run. A request that comes
from another machine or a web page, is too large, is not JSON or contains unknown fields never reaches the business
operation. Documents can be added from any existing local folder; a setting can restrict this to permitted
folders. Field corrections are versioned: a save based on an outdated version is rejected.

```mermaid
flowchart LR
  UI["user interface"] --> API[jav/service/api.py + jav/service/api_*.py<br/>local service]
  CLI[command line: wp-*, run-*] --> VIEWS
  API --> VIEWS[jav/app/work_views.py<br/>shared views]
  API --> CORR[jav/app/corrections.py<br/>field correction]
  VIEWS --> WORK[jav/app/work.py]
  CORR --> WORK
  WORK --> Q[job queue]
  W[worker + lock] --> Q
```

## 9. Source-grounded review

**Plain-language summary.** When a run reads the text, it also saves where each word is (the word layer), and for every
extracted field it computes where the field is on the document (the source location). The review UI draws a box around
the selected field on the document's page image. It also shows the other candidates, and a field can be filled from words
selected on the image. All of this happens in code, without AI calls. If the location is ambiguous, there is no box,
only an explanation: no box is better than a wrong box.

```mermaid
flowchart LR
  LOAD[load_pdf / ocr_pdf] -->|word boxes| SL[(source_layers)]
  DR[decide_route] --> G[ground<br/>jav/ai/grounding.py] --> SAVE[save<br/>datapoints.provenance]
  SL --> G
  SAVE --> API[/api/runs/…/items/…<br/>provenance, source/]
  SL --> W[/…/words/]
  PDF[source document] --> IMG[/…/pages/n.png/]
  API --> UI[PageViewer + FieldPanel]
  W --> UI
  IMG --> UI
```

## 12. Data checks, limits and safeguards

**Plain-language summary.** The system is deliberately strict in several places. It checks tax numbers against
recognised formats and the check digit, it does not claim false certainty for a field with no candidates, a damaged
glyph does not turn into a negative amount, and a document without a type pack gets a to-do. The
input limit stops documents that are too large, and the PDF parsers run in a separate helper process with a time and
memory limit, so a broken PDF cannot hang the worker or the service. On the code side the data guard protects what goes to GitHub, on the
browser side the security headers protect the UI, and the running version is visible. The full security picture:
[security notes](SECURITY.md).

## 14. Content-based file names

## 15. Source instances

**Plain-language summary.** When a document is added to a work package, the system keeps an unchanging copy of it, and
everything afterwards works from that copy: processing, the document shown in review, its page images and the named
copies. What a person checks is therefore exactly what the result was made from, even if the original file is later
changed, moved or deleted. A change to the original is shown as a warning, not treated as an error. The copies go into
the daily backup once each.
