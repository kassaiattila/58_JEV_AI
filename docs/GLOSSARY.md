# Glossary

The shared dictionary of the project: every technical term used in the code, the documentation and the user interface, explained in everyday words, together with its Hungarian equivalent.

## Plain-language summary

This glossary explains the project's technical terms in everyday language. Each entry gives the English term, the Hungarian word used in the Hungarian interface and in conversations with the owner, a short meaning and an example. The terms are grouped by topic: the building blocks of the system, work packages and runs, review, results, documents, the AI components, email, measurement, operations and the development process. It is the only dictionary of the project, so every summary, handoff and README section builds on these definitions.

## How to use this glossary

- **Add first, then use.** A new term goes into this glossary before it appears in any text. On its first use in a text, explain it in half a sentence or link here ([CLAUDE.md §8](../CLAUDE.md), [documentation standard](guides/DOCUMENTATION.md)).
- **Hungarian column.** The owner works in Hungarian and the interface shows Hungarian by default, so every entry carries its Hungarian word: use that word in Hungarian text and in conversation. Older or alternative names follow in parentheses.
- **Interface labels** are quoted with their label from the English interface (for example Approve and release); the Hungarian label is in the Hungarian column or in parentheses.
- **Document vocabulary.** Hungarian text printed on documents (for example "fizetési határidő", payment due date) is quoted in Hungarian with an English gloss, because the code and the models match on it.
- **Numbers** use the en-GB format (decimal point); values quoted from documents keep their printed form (for example "54.732 Ft").
- **Planned concepts.** "(planned)" at the end of a meaning marks a concept that has been designed but not yet built.

## System building blocks

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Framework** | keretrendszer | The shared layer every flow sits on: the JEV caller, the config files, the decision rules, measurement and storage. The goal is to assemble a new flow from it rather than build one from scratch. | A German invoice flow uses the same framework as the Hungarian one. |
| **Flow** | flow (folyamat) | The sequence of steps a document or email passes through: reading → questions to JEV → decision → saving. The three reference flows are invoice data extraction (M2), document type recognition (M1) and email intent (M3). | A PDF arrives → at the end we know its type, and it has been saved. |
| **M1 / M2 / M3** | M1 / M2 / M3 | Short names of the three reference flows: M1 is document type recognition, M2 is data extraction (starting with invoices), M3 is email intent recognition. We measure the quality of the framework on them. | "The S path of M2" = the invoice data extraction path in which code searches for candidates. |
| **Burr** | Burr | The library that runs the flows: it describes the steps and transitions as a graph and logs every run. | The flow diagrams in the documentation are generated from it. |
| **Pydantic AI** | Pydantic AI | A library for describing up front the structure of the result expected from the AI, and then calling the model with it; besides generative models it also supports JEV. A correct structure does not guarantee a true answer. | The language is one of the listed options; the yes-probability is a number between 0 and 1. |
| **Adapter** | adapter | The single gateway to JEV. It remembers earlier answers (cache), logs every call and its cost, retries on errors and, when JEV is unavailable, puts the case in the manual queue instead of failing the flow. | The same question asked a second time: 0 HUF, instant answer. |
| **Call site** | hívási hely | A specific point in a flow where JEV is asked, with its own question set and config file. Families: type recognition (broad and detailed), email intent, field selection (Hungarian, foreign and utility invoices) and verification (per type); each has its own config file. | The "invoice field selection" call site sends three question packages per invoice. |
| **Store** | adattár | The local database (SQLite) holding the processed documents, extracted data, emails, the items awaiting manual review and the call log (ledger). The interface calls it the database (for example Database backup). | The recognised type of every processed PDF is stored here. |
| **Ledger** | ledger (hívás-napló) | The store table with one row for every JEV and GPT call: when, which step, how many tokens, what it cost, whether it came from the cache, whether it failed. See also call log. | Today's cost is read from here. |
| **Local service** | helyi szolgáltatás | The shared gateway to the framework for the interface and the command line: a program that accepts requests only from the same machine. It rejects requests from other machines or from foreign web pages, and lets only requests with a validated structure and a bounded size through to processing. The technical term is API. | The `serve` command or `scripts\dev.ps1 start`; address `http://127.0.0.1:8930`. |
| **Endpoint and endpoint list** | végpont és végpontlista | An address of the local service that the interface or a program calls (for example the health endpoint). The endpoint list is the machine-readable description of every address (`/api/openapi.json`). | `/api/health` |
| **Fingerprint (hash)** | ujjlenyomat (hash) | A short identifier computed from the content of a file or text: if the content changes by a single letter, the fingerprint changes. It shows whether a document or config file has changed, and it lets a value appear on a list without its readable form. | The config file's fingerprint in the call log. |
| **Run-bound response log** | futáshoz kötött válasznapló | A copy of the actual requests and responses of one processing run, kept in order. Earlier decisions can be replayed exactly from it. The shared cache, by contrast, may hold a later answer to the same request, so on its own it does not prove what happened in the earlier run. | — |

## Work packages and runs

### Work packages

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Work package** | munkacsomag | A group of documents and emails from one source (folder, upload, mailbox) that are handled together. It has one set of processing settings, and it can have several runs. The concept comes from the legacy AIFLOW V4. | "September utility bills": 14 PDFs from one folder. |
| **Work item** | munka / munkatétel | A document or email to be handled, with a stable identifier; it can have several processing runs. | An invoice awaiting correction in the Work items (Munkák) view. |
| **Item kind** | tételfajta | What an item of a work package is: a document (a file whose type is recognised from its content), an email (its attachments are documents of the same package) or a statement read from a bank's tabular export. Since 177 each kind is described once (`jav/app/item_kinds.py`): whether it is copied when added, whether it gets a document record and a unified name, whether its type is recognised, whether it has a page image; the shared code asks this instead of naming the kind. | An email gets no unified name; its PDF attachment does. |
| **Source kind** | forrásfajta | Where a work package that only processes its items comes from: a folder, a watched folder, files chosen by hand, an upload or a mailbox. A package that runs a logic pack has the logic pack's kind instead. Described once since 177, with what the package's page adds for it. | A mailbox package shows how many PDF attachments are not yet items. |
| **Work folder / watched folder** | munkamappa / figyelt mappa | A folder set in Settings that the worker checks at intervals: new PDFs become a work package (one shared package, or one per day). The folder is only read; the package gets the default processing settings, but no paid run starts on its own. | "Incoming invoices", daily packages, checked every hour. |
| **Hidden (archived) work package** | elrejtett (archivált) munkacsomag | A package taken off the list. Its runs, call log and results are kept, it can still be opened directly, and the list shows it again with the Hidden packages too filter. A watched folder does not add new documents to a hidden package; it starts a new one instead. Only a package that never had a run (it may still contain documents) can be deleted permanently, after confirmation; the fact of the deletion stays in the log. | A test package created twice by mistake, with 0 documents, can be deleted; the package of a closed measurement can be hidden. |
| **Pending item** | függő tétel | A document or email in a work package that no run of the package of the same kind (trial or live) has finished yet: typically one added after the last run. A stopped or superseded run does not count, and an item that failed stays pending. While a package has pending items, its next step is to process them. | Two invoices added after the live run of 100: "2 new items to process". |
| **Removed item** | kivett tétel | A document or email taken out of a work package by a named person with a reason (160-C). Nothing is deleted: the file stays where it is, and the item can be restored. It stays out of the package's next runs; a run already started keeps it, but its result is not released when that run is approved after the removal, and its to-dos do not hold up the approval. | A scanned invoice that came in twice is removed with the reason "a duplicate scan"; the Removed items too switch still shows it, with who removed it and when. |
| **Left-out document (reconciliation)** | kihagyott irat (egyeztetésnél) | A statement or an invoice a named person left out of one reconciliation package with a reason (169). Only that package no longer takes it: the document stays in its own package and in every other reconciliation, and it can be restored. Not possible while a pairing or a ‘needs no invoice’ mark of the package rests on it, or while the package is approved. | An invoice of another company that fell in the period is left out with the reason ‘the other company's invoice’; Left-out documents too still shows it. |
| **Run over the pending items** | kiegészítő futás (a függő tételek futása) | A new run of a work package that takes only its pending items, with their own maximum cost, input and plan (160-C S3). It is offered once a run of that kind (trial or live) has finished some of the package's items while others wait. The earlier runs, their to-dos, corrections and approval stay as they are; its own result is reviewed and approved separately. | After a live run of 100 invoices two more come in: "Live run, pending items only (2)" processes just those two. |
| **Counted run** | érvényes futás | For one item of a work package, the run whose result counts now (168): the latest one that finished the item in an approved live run, else in a live run, else in a trial run. A stopped or superseded run does not count. The package's item list shows it next to each item's state (approved, processed live, processed in a trial, being processed, failed, pending, removed). | After a live run and a later trial, an invoice's counted run is still the live run. |
| **Open live run** | nyitott éles futás | A finished live run of a work package that is not approved, not stopped, and that no later finished live run repeated on all its items (then it is to be superseded instead). A package can have more than one, the oldest is its current run, and a workflow step is not done while one is open. | The live run of 100 invoices still has to-dos while the run of the 2 added ones is approved: the package's next step is the first run's review. |
| **Work package owner** | csomag felelőse | The person from the Users list assigned to the work package. The Only my work packages filter uses it to show one's own packages. It is not a permission: others can work on the package too. | The owner of the September utility package is Teszt Elek. |

### Processing settings and runs

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Processing settings** | feldolgozási beállítások | The few choices that steer how a work package is processed: the processing path (automatic, S, G or GPT only), Azure recognition of weak scans, reuse of earlier answers (JEV and GPT) and, for emails, task proposals. There is one processing for every package: the system handles each item by its kind (an email: intent + attachments; a PDF: type recognition, then extraction of the recognised type), so nothing has to be chosen in advance. Saved as a new version on every change; a package without saved settings runs with the default ones, which are saved when the run starts. Replaced the recipe and the processing profile in the interface (2026-10-01). | Processing path: automatic; earlier answers: reused; Azure: for weak scans; task proposal: off. |
| **Processing path** | feldolgozási út | The first processing setting, one choice of four: automatic (JEV and GPT, the recommended path per document type), JEV where possible (S), GPT + JEV (G), or GPT only, without JEV (processing without JEV). A package of emails only chooses between with JEV and GPT only. On screen since 2026-10-02 it replaces the separate ‘Use of JEV’ switch; the saved settings still keep the path and the use of JEV as two values. | ‘GPT only, without JEV (OpenAI)’: no JEV call, GPT reads and the code checks. |
| **Recipe** | recept (folyamatrecept) | The internal name of a processing description in the code and in `configs/recipes.json`: input, steps, settings and per-item budget, versioned. Since 2026-10-01 the interface offers only one, the processing (`processing`), and calls its settings processing settings; an internal recipe with a document type given in advance (no recognition) remains for tests and command-line measurement, and the two earlier recipes are kept only for old runs. | `processing` v1; `invoice-extraction` (tests and command-line measurement only). |
| **Pre-start overview** | indítás előtti áttekintés | The list on the run card and on the confirmation page saying which services a run may call (local text recognition, JEV, OpenAI, Azure), with the budget maximum and what each is for, and naming the services that will not be called. Documents whose type is not yet known count with the more expensive G path. | "OpenAI up to 0.31 USD: 1 document on the G path; 1 document of a type not yet known…" |
| **Configuration snapshot** | konfigurációs pillanatkép | An unchanged copy of the settings used at run time; later edits do not change it. | The same document later gets a separate run with a new profile. |
| **Run** | futtatás / futás | Processing the fixed input of a work package once, with its processing settings, tracked and with a capped cost. It is either a trial run (changes no business data) or a live run (valid after approval). | A trial run on the September package: 14 items, 3 to-dos, 0.02 USD. |
| **Trial run and live run** | próbafutás és éles futás | The result of a trial run can only be viewed. A live run is approved by a person (Approve and release), and only when every item has finished and no to-do is open. | First a trial with the new settings, then a live run and approval. |
| **Package's current result** | a csomag mostani eredménye | Per item of a work package, the one result that counts now: the latest finished one of an approved live run, else of a live run, else of a trial run, with the person's corrections over the machine values. A stopped or superseded run does not count. The item list's state, name and counting run all come from it (171). Since 174 the reconciliation and the duplicate search read the same result, across every package a document is in; a document removed from every package drops out of them. | An invoice processed in a trial and then live: the live result counts, even if a later trial read it differently. |
| **Approve and release** | jóváhagyás és kiadás | One step on a work package: its open live runs are approved together (each records who approved it and when), and a released package version is recorded (171). | "Approve and release" after the last to-do of the September invoices is settled. |
| **Released package version** | kiadott csomagváltozat | The numbered, downloadable result of an Approve and release: the package's approved items as the downloads were at that moment. Its files are stored, so they never change, even if a label or a rule changes later. A package approved before v1.20.0 got its first version recorded afterwards, marked as such. | Version 2 of the September invoices, released on 18 October. |
| **Released, partly released, changed since the release** | kiadva, részben kiadva, a kiadás óta változott | The release state of a work package. Partly released: an item in use has no released result (for example it was added after the release). Changed since the release: a released item was removed, or another approved result replaced it. The next Approve and release brings it back to released. | A new invoice added to a released package: partly released until the next release. |
| **Measurement (command-line result)** | mérés (parancssori eredmény) | A result processed on the command line, outside any run; it counts only when no run has finished the document (DECISIONS 170 K17). Since 174 the reconciliation, the duplicate search and the statements read each document's result in this order too: approved, live, trial, measurement. | An evaluation's result of an invoice no package has processed. |
| **Readiness check** | készenlét-ellenőrzés | A check before a run: is every required input present, and what needs attention. | The warning "2 PDFs have no text layer, OCR needed". |
| **Fixed input** | rögzített bemenet | When a run starts, the items of the work package and their content hashes are recorded. If a file changes afterwards, the worker does not process it but reports an error. | An invoice PDF was replaced after the start: the item gets a "source changed" error. |
| **Confirmation page** | megerősítő oldal | The trial run, live run and rerun buttons do not start anything straight away; they lead to a summary page: mode, package, processing settings, number of items, highest possible cost and the pre-start overview. A run can only be started from there. | "Confirm starting a live run: 14 items, OpenAI at most 2.10 USD." |
| **Rerun** | újrafuttatás | Repeating a run as a new run, in its mode, on the package's items as they are now (the added ones too, the removed ones not; 160-C S2). Pressing the button twice still starts only one new run; a run in progress cannot be repeated. | After a failed run: fix the OCR, then rerun. |
| **Idempotent start** | idempotens indítás | Starting the same run twice on the same input creates only one run; the second request returns the existing one. | A double click on the Run button. |

### The worker

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Job queue** | munkasor | A durable task list in the store. Every item to be run is one row with a unique key, so the same item cannot be queued twice. The attempt count survives a restart. | The 14-invoice run gives 14 rows; a faulty PDF becomes "dead" after two attempts, and the rest keep running. |
| **Worker** | feldolgozó | The background program that takes the items from the job queue one by one and runs them. Only one runs at a time: a lock guards this, and a second instance does not even start. On request it exits cleanly after the item in progress. | The `worker` command; on start-up it puts back into the queue whatever an earlier stop left half-done. |
| **Orphaned task** | félbemaradt (árva) feladat | The worker was working on an item when it stopped (machine restart, forced stop, crash). On start-up the task goes back into the queue, behind the fresh work. If the same task is left half-done three times, it counts as dead and the item is marked failed, so that it does not bring the worker down again and again. If someone requested a stop while the worker was down, the task is closed as stopped on start-up. | A damaged PDF "kills" the worker three times: on the fourth start the item is failed and the other items run. |
| **State store and thinning** | folyamatállapot-tár és ritkítása | After every step the worker saves the full state of the flow, so that it can resume from there after a stop. For a finished item only the last save is needed, so the others are deleted (thinning); compaction then returns the freed space to the disk. | A finished item with a dozen saved steps keeps only the last one. |

### Cost and budgets

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Budget** | keret (költségkeret) | The cost limit of a run, per provider (OpenAI and JEV): the sum of its per-item cost budgets. Every paid call reserves from it first (cost reservation); the owner's overall budget and sub-budgets sit above it. In Hungarian "keret" also means a box on the page image; the context tells which is meant. | A run with a 1.00 USD budget. |
| **Call log** | hívásnapló | For every paid model call (GPT, JEV) an entry is written BEFORE the call and completed afterwards with the actual model and cost. Failed calls are included. | A timeout is a "failed" entry with an unknown cost; the budget counts it at the highest possible amount. |
| **Cost reservation (budget reservation)** | költségfoglalás, más néven keretfoglalás | Before a call, an upper bound of its cost is reserved from the run's budget. It is a real bound, not an estimate: at most one token per byte of everything sent, plus a fixed overhead, for every possible retry. If it does not fit, the call does not start; if a call still costs more, the run makes no further call with that provider. With a known cost the unused part is released; with an unknown cost it stays reserved. | With a 1.00 USD budget, after 0.99 USD a call that may cost up to 0.20 USD no longer starts. |
| **Sub-budget** | részkeret | A cost limit for a particular measurement or trial, approved in advance by the owner within the overall budget (OpenAI and JEV separately). A new decision is needed before it is exceeded; old sub-budgets cannot be merged. | "0.50 USD of JEV for a re-measurement after a question change" |
| **Per-item cost budget** | tételenkénti költségkeret | The maximum amount the system reserves per item (document, email, attachment) and per provider when a run starts. The run's total budget is the sum of the item budgets. It is an upper limit: the actual cost is usually lower and can be followed on the run's page. The budget depends on the chosen path and the settings (for example, task proposals, when switched on, add an extra amount per email). | Invoice, G path: JEV at most 0.05 USD, OpenAI at most 0.15 USD (0.10 USD before v1.1.0), Azure DI at most 0.02 USD per item. |
| **Actual cost** | tényleges költség | What the paid calls of an item, a run or a work package really cost, per provider and model, read from the call log. A call whose cost is not known is not part of it; its reserved amount is shown apart. Shown next to the budget, which is only an upper limit. | ‘JEV · jev-1.13.0: 0.0020 USD’ on an item |
| **Answer from an earlier answer** | korábbi válaszból kapott kérdés | A question the system did not pay for again because the same question was already answered (an earlier JEV or, since 2026-10-02, GPT answer, or the text of an earlier Azure recognition). It costs nothing and is counted next to the actual cost. | ‘12 questions answered from earlier answers (free)’ |
| **Reserved, outcome unknown** | lefoglalt, ismeretlen kimenetelű összeg | The reserved maximum of paid calls whose cost is not known (failed or interrupted attempts). The budget keeps counting it, to be safe, but it is not an actual cost. | An Azure attempt that failed because the service was not running |
| **Planned and actual** | tervezett és tényleges | On the run's page, per provider: what the pre-start overview expected (expected, possible, not expected, with the budget) next to the actual calls and cost; a warning if a provider was called against the overview. | ‘OpenAI — Plan: not expected; 1 paid call’ with a warning |
| **Uncertain attempt** | bizonytalan kísérlet | A paid call of which we do not know whether it went through, for example because the program stopped in the meantime. It is not repeated automatically, because we would pay twice; it has to be settled by hand. A call that another running program (for example a measurement started from the command line) is still waiting on does not become uncertain when the worker starts. | A stop after the GPT response but before saving. |

## Review and correction

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **To-do** | teendő | A reason on an item that calls for human review. To-dos can be resolved reason by reason; closing one reason does not close another. | "The invoice total does not match the sum of the line items." |
| **Review queue (manual queue)** | review-sor (kézi sor) | The store's list of the cases that the rules say a person has to look at, with the reasons. | "Uncertain type, 0.45" |
| **Review reason** | review-ok | A short machine code saying why a case went to the manual queue; a case can have several; once written it is never removed (the process can only become stricter). | "Uncertain field: bank account 0.56" |
| **To-do kind** | teendőfajta | What kind of to-do a reason is: its first two parts (`pick:low_conf`, `jev:absence_wrong`), or a family whose second part varies (each code check, each JEV error). Since 177 every kind is listed once (`configs/todo_kinds.json`) with the modules that raise it and an example, and the interface's test checks that each kind has a label instead of its raw code. | `jev:absence_wrong`: JEV says a field was left empty though it is on the document. |
| **Earlier to-do** | korábbi teendő | An open to-do on a document that was raised not by the run being viewed but by an earlier measurement or run. It is shown, but it does not block the current run's status or approval. If the current run raises the same reason: for a trial run, the reason moves over to it; a reason belonging to a live run that has not been approved yet stays where it is, and the current run gets its own row, so the earlier live run cannot be approved without review either. The earlier to-dos left by trial runs are hidden on the review page by default (a trial run cannot be approved, so they never close by themselves); a switch shows them. | An "uncertain bank account number" to-do from an old measurement, on an invoice that has just run without errors. |
| **Superseding a run** | futás leváltása | A person sets aside an older live run that is not approved when a later live run of the same package has processed the same documents again. The older run stays as a stopped run, its open to-dos close (they are kept), and it cannot be approved any more; corrections and closed to-dos made on it stay with it. Since 200 an older trial run with open to-dos can be superseded too, by any later run of the same documents (trial or live); that only closes its to-dos. A later trial run never supersedes a live run. | Of two live runs on the same 100 invoices, the older one is superseded, and its 142 to-dos no longer show as earlier to-dos on the newer run's page. |
| **Field correction** | mezőjavítás | A field value corrected by a person on an item of a run. The machine-extracted data stays unchanged next to it; the corrections form a separate, versioned series. If someone else has saved in the meantime, the save is rejected (no silent overwrite). | The invoice number is corrected from "MINTA-1" to "MINTA-1/A"; the report shows the corrected value, and the machine value can still be traced. |

| **Activity registry** | tevékenység-nyilvántartás | The one list of what people do and what the logs record: the actions a package's or a workflow's log may record (each with its label), where "My work today" reads a person's actions from, the kinds of decision that make up a run's reviewed version, and the task kinds an email's task proposal may name. A log refuses an action that is not on the list (175). | Approving a reconciliation version is a registered action, so it always shows with its label. |
| **Check registry** | ellenőrzés-nyilvántartás | The list of every check a document's result goes through, in four stages: the record itself (sums, dates, tax numbers), the decision (which AI judgement or failed check becomes a to-do), the comparison with other documents (duplicate invoice, own tax number, overlapping statements), and the scans of the stored results afterwards. The order of the checks, and so of the to-dos, is fixed; a check that reads other documents runs only in a package's run, never in a measurement (175). | A new check is one entry with its stage, not a change in several places. |
| **Type role** | típusszerep | What part a document type plays in the processing: incoming or outgoing invoice, bank statement, utility invoice, and which checks look at it (duplicate search, own tax number). Each role is a list in the settings; since 175 the code reads every role from one place, and a test checks that the lists agree, so a new type left out of one list is caught instead of silently missing a check. | The electricity invoice is an incoming invoice and a utility invoice, and the duplicate search and the own-tax check look at it. |
| **Base pack (extends)** | alap-csomag (extends) | A type pack inherited by several types: the 19 shared fields, required fields and checks of the utility invoices in one place; the six utility types add only their own extra fields. It cannot run on its own (it has no prompt). | Electricity = base + 10 own fields (meter reading, consumption, tariff…). |
| **Field kind** | mező-fajta | The category assigned to every field in the type pack (name, tax number, date, amount, bank account, currency, country, invoice number, address, text, number). The kind decides how the value is normalised, how it is compared with the golden set, and which candidate finder supplies candidates for it. | "gross_total: amount" → a decimal number, compared as a number. |
| **Informative field** | informatív mező | A field we extract and report, but which under the legacy scoring contract does not count towards accuracy, and whose uncertainty alone does not send the item to the manual queue (the address; on foreign invoices, the bank account too). The exception is a high-stakes field (the Hungarian IBAN): it goes to the manual queue even when it is informative. | The supplier's address does not match "exactly" because the golden set leaves out the country — not an error. |
| **Document without a type pack** | típuscsomag nélküli irat | A document whose type was found by recognition, but for which there is no extraction type pack yet. It gets a to-do instead of passing silently. | A certificate of completion (teljesítésigazolás). |
| **Teaching a document type** | típus megtanítása | Recording a versioned type description, examples, structure, reading methods and error rules, then checking them on separate samples. It is not retraining JEV's weights for each customer. The full workflow is still a plan. | Recognising a new statement type and reading multi-line transactions. |
| **General data proposal** | általános adatjavaslat (általános tények) | What a document without a type pack gets instead of a type's fields: GPT proposes facts (a thing, its property and value), code checks each one word for word against the source text, and JEV judges whether the text supports it. Such a document is marked for review. | A certificate of completion's date, parties and amount as facts. |
| **Development half / evaluation half** | fejlesztési fél / ellenőrző fél | A held-out family's documents, split in two before any measurement (197). A taught type's draft is written and corrected from the development half only; the type is then measured once on the evaluation half, which it has not seen. A result on the development half is a check on its own training sample, not evidence. | 5 + 5 admission tickets. |
| **Taught type** | tanított típus | A type pack made by code from a draft a person wrote from the general facts of a family's development half (197). The draft is the only file a person edits. | The taught admission ticket. |
| **Candidate pack** | jelölt csomag (jelölt típus) | A taught type pack that detection does not pick yet. It can be measured and run with an explicitly chosen type, but it changes no processing until it is turned on. Not the same as a candidate value of the S path. | The taught ticket before it was turned on. |
| **Turning a type on / withdrawing it** | típus bekapcsolása / visszavonása | The person's command that lets detection pick a type pack in its family, or stops it (199). The files stay, so earlier results keep their type. A taught type is turned on only with a measurement of its evaluation half on its current files; it can take over the family's old pack in the same step. | The taught ticket replaces the converted ticket pack. |
| **Package draft and structural certificate** | csomagtervezet és szerkezeti bizonylat | A package draft is the editable description of a new document type, with its fields and processing settings. The structural certificate records whether the checked references and data types are in order. It does not prove extraction accuracy and does not activate the type. | — |
| **Data-point discovery** | adatpont-felfedezés | Proposing meaningful fields, values and relationships in previously unregistered text, with their source and an uncertainty signal. The full standalone capability is still to be developed. | Machine, temperature and time from a maintenance note. |

### Text, OCR and word positions

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Text layer** | szövegréteg | The copyable text stored in a PDF. PDFs from invoicing software have one; scanned (photographed) invoices do not, and there the PDF is only an image. | A scanned utility bill is an image without a text layer. |
| **Word layer** | szóréteg | All the words of a document with their positions on the page, as the run read them. The boxes are drawn from it; no AI call is needed. | "12 700" is two words in line 3, on the right half of the page. |
| **Lost glyph** | elveszett betűjel | The font of some PDFs does not yield a character (a hyphen, a "+", a letter pair) in the text; an invisible control character (NUL) stands in its place. Between two letters or digits it has so far always been a hyphen, so there we read it as a hyphen; elsewhere we do not guess. | An invoice number of the form "AB12CD34-0009" used to come out in two pieces ("AB12CD34" and "0009"). |
| **Protected line boundary** | védett sorhatár | A page or structural boundary across which the program does not allow lines to be joined. | — |
| **OCR (optical character recognition)** | OCR (optikai karakterfelismerés) | A program that "reads" the letters and digits in an image and turns them into text. It can make mistakes: accents disappear or get garbled (György → Gyorgy, ö → é), letters and digits get mixed up (A1 → Al), a digit is dropped. | "54.732 Ft" read correctly, but "Féldgazhalozati" instead of "Földgázhálózati" (gas network). |
| **OCR pipeline** | OCR-lánc | The chain of steps: the pages of the PDF are rendered as images (300 dots per inch), OCR runs on the image (tesseract, with the Hungarian + English language packs), and from the positions of the recognised words we build lines and column cells just as for a PDF with a text layer. From there on, the flow does not know that it received OCR text. | A scanned multi-page bill takes tens of seconds. |
| **Native OCR / Docker OCR** | natív OCR / Docker-OCR | Native = the tesseract program installed on the machine (fast, a few seconds per page). Docker = the legacy project's container image, which also contains it; this is the fallback, because it can be many times slower, for example when Docker shares the processor with many other containers. | The automatic engine choice takes native OCR; Docker only when native tesseract is not installed. |
| **OCR confidence (word confidence)** | OCR-bizalom (szó-bizalom) | OCR gives every recognised word a number between 0 and 100: how sure it is. The average (stored on a 0–1 scale) and the share of weak words (below 60) are the document's OCR quality signal; the threshold is in the config file, and below it the document goes to the manual queue. | Electricity bill: average 0.87, weak words 11%. |
| **OCR cache** | OCR-gyorsítótár | A document's recognised text is written to disk (the key is the file's fingerprint + the OCR settings + the tesseract version). The second time, the same document runs instantly, without OCR. That is why golden measurements are slow only the first time. | A golden run: slow the first time, almost instant afterwards. |
| **Azure Document Intelligence (Azure DI)** | Azure Document Intelligence (Azure DI) | Microsoft's cloud OCR service: we send the image and get back text and word coordinates, much more accurately than with the local tesseract, but it is paid per page and draws on the legacy sidecar's page allowance. Here it is reached through the legacy sidecar, in two ways: OCR escalation (below) calls it automatically, and a measurement can force it with `JAV_OCR_ENGINE=azure_di`; the `auto` engine choice never picks it. | A scanned bill on which the local OCR is weak. |
| **OCR escalation** | OCR-eszkaláció | Two-stage OCR: the free local tesseract runs first, and the paid Azure service is called only if the local result is weak (the average word confidence or the share of weak words falls outside the threshold in the config file). The decision is data, not code; the raw run shows when escalation happened. Escalation is switched on in `configs/ocr.json` and runs automatically, but only if the legacy sidecar is running and can reach the file; otherwise the local result stays. The **Azure recognition** (*Azure-felismerés*) processing setting decides it for a run: when it is on (the default), each document may use the run's Azure budget (0.02 USD by default, about 13 pages at the list price), every call goes into the call log, and if the budget runs out the local text goes on with a to-do. | With the default thresholds (average word confidence 0.93, weak words 10%), a document below the first or above the second escalates. |
| **Taken-over Azure recognition** | átvett Azure-felismerés | When a scanned document whose type has no type pack continues into general facts (124), the native reader uses the Azure recognition the system already has, or one asked for within the run's Azure budget, instead of its own local OCR. Azure's original answer is kept beside the reading and checked against the document's pages; a page it does not fit stays unread with a reason, and local OCR is never mixed in. Such a reading can be complete; weak word confidences raise a to-do. | "Read by Azure: page 1, mean word confidence 0.97" |

### Candidates and fields

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Candidate** | jelölt | On the S path, a possible value collected from the text by code (a number shaped like a tax number, a date, an amount, a name). JEV chooses only among these, or says "none of them". | "12345678-1-42" is a tax number candidate. |
| **Candidate profile** | jelölt-profil | The rule set (regexes) of the candidate finders, chosen per type pack: the Hungarian one (`hu`) is the existing set of the Hungarian invoice, unchanged; the international one (`intl`) knows EU / Turkish / Polish / US tax identifiers, the `$1,600.00` notation and foreign legal forms. Dates are read the same way on every profile (see uncertain order of day and month). | An English-language foreign invoice: "Dec 5, 2025" is a date candidate only with the international profile. |
| **Labelled text field** | címkés szöveg-mező | A free-text field that has a label on the document ("Árszabás:" (tariff), "A szolgáltatás megnevezése:" (name of the service)). The code offers the text after the label (in the same cell, in the next cell or below the line) as a candidate, and JEV chooses. | Tariff: „ESZ "A1" Lakosság” (residential). |
| **Quantity candidate** | mennyiség-jelölt | Candidates for consumption, meter reading and calorific value: only the numbers on lines with a unit or a meter label (kWh, m3, MJ, mérőállás (meter reading), Leol (reading)), so that the request does not grow too large and JEV sees the unit next to the number. | "882 kWh", "(143,00 m3)" |
| **Uncertain order of day and month** | kétes nap–hónap sorrend | An all-number date whose day and month can be read two ways (04/12/2022: 4 December or 12 April; 04.12.22 may also be the Hungarian short form with the year first) and which the document's other dates do not decide. The system keeps one reading but raises a to-do; it never guesses silently. A typed date of this kind is refused: type it with the year first or with the month's name. Dates with a month name ("04-DEC-22", "4 December 2022") or with the year first are never uncertain. | "04/12/2022" on an invoice whose other dates are all below the 13th. |
| **Recognised tax ID format** | felismert adószám-alak | A notation known to the tax ID check: the Hungarian tax number and the Hungarian EU VAT number (both with a check digit), the tax number formats of the EU countries, the EU one-stop-shop registration number, and a few common non-EU formats (British, Norwegian, Swiss, US). The code strips the label and the prefix first; anything still unrecognised (a phone number, two identifiers in one field) gets a to-do. | "VAT ID: IE 1A12345 B" → "IE1A12345B", a recognised Irish format. |
| **Reverse-charge rule** | fordított adózás szabálya | A code rule in the international profile: if the invoice says "reverse charge" / "fordított áfa" but has no 0 amount anywhere, the code offers a "0" VAT candidate — because JEV can only choose an offered value, and under reverse charge the printed VAT is 0. | A reverse-charge foreign invoice: VAT = 0, although only the label is printed on it. |
| **Source candidate** | forrásjelölt | An excerpt judged suitable for answering the given question, which can be traced exactly in the original text. It is not yet an accepted, normalised data point. | The line containing the amount payable, with its surroundings. |

## AI components

### Models and extraction paths

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **JEV** | Jev (JEV) | TypeSafe's AI model, which does not write text but **gives decision signals for closed questions**. It does not generate new values, but it can pick the wrong one of the options offered. The signal is not the probability that the whole document is correct; time and cost are measured on our own samples. | "Is this number the supplier's tax number?" → a yes-signal of 0.97 |
| **S path and G path (S arm and G arm)** | S-út és G-út (régebben S-kar és G-kar) | The two ways of extracting invoice data. **S path**: code finds the possible values, JEV chooses among them. **G path**: a text-generating model (GPT) extracts the data, and JEV verifies it field by field. Currently the two paths decide separately; an agreement gate between them is only planned. S arm and G arm are older names for the same thing; the interface and the newer reports say S path and G path. | S path: "which of the 9 numbers found is the gross amount?" |
| **Recommended path / automatic path** | ajánlott út / automatikus út | The type pack can say which path the extraction takes by default: code + JEV (S) or GPT + JEV (G). The automatic path setting follows it; an explicit request for S or G takes precedence (an S request runs on G for a type that only has a G path). | Utility invoice: G, because one GPT call gives both the header data and the line items; Hungarian invoice: S. |
| **Second opinion, path escalation** | második vélemény, út-eszkaláció | Every document goes down the cheaper S path; the G path runs a second time only on those where a to-do remains, just as Azure follows the local OCR. This way the more expensive path only touches the difficult documents. (planned) | A foreign invoice left with a to-do on the S path also goes through the G path. |

### JEV question kinds

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Choice** | Choice (választás) | "Which of the listed options is it?" — JEV gives a probability for every option and picks the most likely one. There is always a "none / unknown / other" option. At most 255 options. | Document type out of 13 options. |
| **Noul** | Noul (igen/nem) | "Is this statement true?" — a single number between 0 and 1: the probability of "yes". | "Is the issuer a Hungarian company?" → 0.97 |
| **Score** | Score (fokozat) | "Where is this on a scale?" — 2–10 levels, each described by a concrete situation (not "medium" but "reminder, deadline within a few days"); meant for degrees (urgency, severity), not for yes/no. The answer: a probability for every level, the most likely level, and an expected value (the probability-weighted average of the levels). We use it for email urgency. | Urgency: 0 no time pressure … 3 final demand; expected value 1.8 = around level 2. |
| **Criterion** | kritérium | The description of a Choice option that JEV reads: what it is (what), what it is NOT (not_for), examples. Accuracy depends on it. | "Hungarian invoice: … NOT: a foreign issuer with a Hungarian buyer" |
| **Instruction** | instrukció | The text of the question, in English (JEV is most accurate in English); the document text, however, is sent in its original language. | "Which value is the SUPPLIER's tax number?" |
| **State** | állapot (state) | The data package sent with the question: selected lines of the document and signals computed in code. Only what the question uses goes into it. | The first 40 and the last 8 lines of the invoice. |
| **Presence question** | jelenlét-kérdés | A Noul next to every field selection: "is this field on the document at all?" This way JEV does not confidently pick a wrong value when the field is missing. | "Is there an IBAN or bank account number on the invoice?" |
| **Batched request** | kötegelt kérés | Several questions in one call on the same state; JEV evaluates them in parallel, and they do not see each other's answers. The shared text is given once, but the questions also consume tokens and cost. | 6 field selections + 6 presence questions in one request. |
| **Structured question (structured instruction)** | szerkezetes kérdés (strukturált instrukció) | The question is not one glued-together sentence but a labelled package, with separate slots for the field's meaning, the extracted value, the lines where the value appears, and the question itself. The JEV documentation recommends this when part of the question is produced by code (for example the same question for every field, only the value differs). | "field: supplier tax number · extracted: 12345678-1-42 · line: L02 · question: is this a different kind of number?" |
| **Verification question (error flag)** | ellenőrző kérdés (hiba-flag) | The second step of the G path: yes/no questions for every field of the generated extraction about whether it is wrong (another field's value ended up here; truncated; a different kind of number; wrongly empty; parties swapped; a missing line item). "Yes" means an error; above the yes band the case goes to the manual queue. | "Is the supplier name truncated?" → 0.97 → manual queue |
| **Source localisation (finding the source location)** | forráslokalizálás / forráshely keresése | Determining on which page, line or text block the data sought is found. It is not guessing the value itself: the code copies it from the original source. | Selecting the line that contains the invoice number. |
| **Structure recovery** | szerkezet helyreállítása | Recognising the lines and text parts that belong together: header, item, summary. The original text is kept; only the grouping changes. | Attaching a product name broken over two lines to one item. |
| **Source-based verification** | forrásalapú ellenőrzés | Comparing an extracted claim with the original text: the source supports it, contradicts it, or does not discuss it. | The number is on the page, but it belongs to the buyer, not to the supplier. |
| **Request-size budget** | kérés-méret keret | JEV accepts only a limited amount of text per request (beyond it, it returns a "max_tokens_exceeded" error). The call site's setting: if the request is too large, the code first narrows the text to the candidates' lines, then shortens the option descriptions, and finally reduces the number of candidates — in document order, so that the parties at the top of the invoice are not dropped. The same applies on the verification path: only the evidence lines are sent instead of the full text. The budget is measured in characters and JEV counts tokens, so an overflow can happen even under the budget: the code then retries once with a narrower question and gives up only after that (manual queue). The reduction is visible in the raw run. | A long bundle with many name candidates: those that fit are kept, in document order. |

### Decisions and thresholds

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Confidence** | confidence (magabiztosság) | For a Choice: how concentrated the probability is on one option (0–1). It is not the same as the probability of the most likely option, but close to it. | 0.99 = almost certain |
| **Processing without JEV** | JEV nélküli feldolgozás | The ‘GPT only, without JEV’ processing path (until 2026-10-02 the ‘Use of JEV’ switch, off): GPT recognises each document's type and each email's intent, and extracts the data on the G path; the code checks every extracted value against the document text; the run gets no JEV budget, so no JEV call can happen. The path and JEV-answer settings do not count then and are not shown. | Use of JEV: off — GPT only (OpenAI). |
| **Refusal without JEV** | védőháló (JEV nélküli feldolgozásban) | In processing without JEV, a JEV question that a step would still ask is not sent: it gets no answer, not even an earlier one from the cache, and the item gets the to-do ‘The JEV question was not sent: this processing runs without JEV, on GPT only’ (*A JEV-kérdés nem ment el, mert ez a feldolgozás JEV nélkül, csak GPT-vel fut*). It makes ‘GPT only’ a guarantee; in the tests such a question fails the test. | since 2026-10-17 |
| **AI engine** | AI-motor (JEV + GPT, vagy csak GPT) | Which AI the processing asks: JEV and GPT (the default, the measured way) or GPT only, without JEV. The application has one setting (Settings › Processing); a workflow step and a package may choose their own, and a run keeps the engine it started with. A new package, a package whose settings were never saved, a mailbox download and a watched folder take the application's; saved settings keep theirs. | ‘AI engine: GPT only’ on a workflow step: its package runs without JEV, whatever the application's setting. The same mark stands beside the approval and on the Review bar of a run that ran without JEV. |
| **Engine matrix** | motor-mátrix (ellenőrző lista a JEV-hívási helyekről) | The list of every place where the system asks JEV, each with what does the same step without JEV (a GPT question or a check in code) or a stated reason why nothing does, and the tests that cover it. The session-start check fails while a place is missing from it. | 34 places, 22 with a counterpart |
| **Paired test** | páros teszt | An automatic test that runs the same flow twice, once with JEV and once with GPT only, and checks that both reach the same kind of result. | every type pack's extraction both ways |
| **GPT confidence** | GPT-bizonyosság (a válasz valószínűségéből) | How sure GPT was of its own answer, computed from the probabilities it gave to the pieces (tokens) of the answer. It is GPT's own estimate, not calibrated like JEV's: GPT can be very sure and still wrong, so code checks are still needed. When it cannot be measured, the item gets a to-do instead of a guessed value. For a field GPT extracted without JEV, this is the field's estimate, lowered when the field fails its field check; it has its own band (green only from 98%). Below 98% on an accounting field it is also a to-do (only without JEV; an address or another informational field only shows it). | An email intent at 0.56: below the threshold, so it goes to the manual queue. |
| **Band** | sáv | Splitting the raw probability into ranges for the decision. For a yes/no question: no (< 0.30) / uncertain / yes (≥ 0.70). For a choice: automatic (confident) / uncertain (the second option is too close) / manual (below the threshold, currently 0.60). The thresholds live in config files, not in code. | 0.45 confidence → manual band |
| **Second-option gap** | második-lehetőség rés | The difference between the probabilities of the most likely and the second option; if it is small (< 0.20), the choice falls into the uncertain band. | 0.55 vs 0.45 → gap 0.10 |
| **Threshold** | küszöb | The boundary of a band. It can only be changed in the config file, with a version number; after a change, old runs can be re-evaluated without calls. | Manual band boundary 0.60; 0.85 for high-stakes fields. |
| **High-stakes field** | magas tétű mező | A field where an error is expensive (amount payable, due date, bank account, tax number): the threshold is higher here. | A gross amount at 0.84 is still manual. |

## Measurement and quality

### Golden set and scores

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Golden set** | etalon (etalon-készlet, golden) | Hand-checked, "certainly correct" examples: invoices with every field, documents with their type, and emails with their intent. Current sizes and results are in the state snapshot (`docs/STATE.md`, local). The system is measured against them. They stay in the legacy project because they contain personal data. | A golden invoice with every field checked by hand. |
| **Synthetic golden case** | mesterséges etalon-eset | An invented document with its expected values, for a situation the golden set does not cover (a credit note, a receipt without an invoice number). It contains no real data, is committed to the repository and is measured apart from the golden set, so the earlier results stay comparable. It shows whether the rule works on the case it was written for, not general accuracy. | An invented credit note that prints its own number and the original invoice's: the expected answer is its own number. |
| **Shared measurement command** | közös mérőparancs | One command that measures every golden set the same way: the data points of each document type, the type recognition, the email intent and the golden sets of the logic packs (the reconciliation's). Without a budget it uses only earlier answers, so it is free; a paid measurement names one golden set. Each round leaves a receipt with the code version it measured. A new logic pack names its golden set in its own registration, and the command measures it too. | 188: `measure` measures 26 golden sets from earlier answers; `measure reconcile` only the reconciliation's two. |
| **Accuracy** | pontosság | The share of correct answers on the golden examples. Always give the count next to the percentage. | 9 of 10 fields correct: 9/10 = 90% |
| **Candidate recall** | jelölt-lefedettség (recall, jelölt-recall) | The part of the golden values that can be found among the candidates collected by code. JEV can only choose from candidates, so this is the best result the S path can reach. It can be measured without AI calls, for free: `python -m jav.cli recall`. | 10 of 12 golden values are among the candidates: the S path can get at most 10 right. |
| **Coverage of selected fields** | kijelölt mezők lefedettsége | How many of a predefined set of data items the system found in the right role. It says something only about those fields. | 16 requested values appeared; the completeness of the other fields is unknown. |
| **Presence truth** | jelenlét-igazság | The golden reference for the presence question: whether the field is filled in according to the golden set. | One invoice has no bank account → "no" is the correct answer. |
| **OCR-tolerant match** | OCR-tűrő egyezés | A second, informative score in the golden measurement: names, addresses and text are also compared without accents, case and punctuation. The difference between the strict and the OCR-tolerant figure is what only the OCR's accent noise spoiled. | "Gyorgy" for "György": wrong under the strict score, correct under the OCR-tolerant one. |
| **Calibration** | kalibráció | Whether what an AI says about its own certainty is true: are its 90% answers really correct 90% of the time? Measured for JEV and, since 2026-10-17, for GPT too (the GPT confidence of a type, an intent or an extracted value). One number for the deviation is the ECE (0 = perfect). | ECE 0.01 = very well calibrated |
| **Determinism measurement** | determinizmus-mérés | Asking the same question several times without the cache, and checking whether the answer changes (a label change = flip) and how much the probability fluctuates. | Every golden invoice asked 3 times: does any label flip? |
| **Cache** | gyorsítótár (cache) | The adapter stores the answer for every (model version + state + questions) triple; asking the same question again is free. Any change to a question or description gives a new key, and so a new live call. | Rerunning the golden set costs 0 HUF if nothing has changed. |
| **Pre-estimate** | előbecslés | A free dry run of a planned paid measurement: the measurement runs as it will, but JEV is replaced by a stand-in. Questions already in the cache get their saved answer; missing ones are counted and priced from their size but never sent. It tells how many live questions the measurement will ask and roughly what it will cost before any money is spent. | 1,060 questions, 310 of them live: about 0.40 USD. |
| **In-sample (measured on the training examples)** | a tanító példákon mért (in-sample) | When a rule is tuned on exactly the examples that are then used for measuring — a good result is then not evidence, only a signal. This must always be stated. | A perfect score after a sentence tailored to one of the measured emails. |
| **Raw run** | nyers futás | The complete, row-by-row result of every measurement, in a file; the report is built from it, and it can be re-evaluated without calls. | Every number in the report can be traced back. |
| **Eval report** | eval-riport | A one-click summary of the raw runs: accuracy per question, bands, calibration, how many cases would change band after a threshold change, determinism, and the silent errors. It reads the measurements made without JEV as separate lines (named "…_gpt"). | "How many cases would go to the manual queue if we tightened it" |
| **Silent error** | csendes tévedés | A wrong answer (a type, an intent or a value) that passed without a to-do, so nobody would have looked at it. The eval report counts them per measurement; they are what a confidence threshold has to keep low. A wrong answer that got a to-do is not silent: a person sees it. | GPT read a Hungarian invoice as foreign with 100% confidence and no to-do: one silent error. |
| **Verifier probe** | ellenőrző-szonda | Measuring the verification questions without generative calls: JEV gets the correct golden extraction (on which it must flag nothing) and deliberately broken variants of it (parties swapped, truncated name, empty invoice number, gross instead of net, phone number as tax number), on which the matching error flag must fire. The result per band: how many broken variants fell into the yes, the uncertain and the no band. | Every golden invoice with 4–6 broken variants. |
| **Injection probe** | beszúrt-utasítás szonda | Measuring the prompt-injection signal: golden emails in a clean version and with an instruction to the processing system inserted at the start (Hungarian and English, three wordings) or at the very end (English). It counts how often the signal flags the instruction, how often it raises a false alarm on a clean email, and whether the inserted sentence changes the recognised intent. A small trial, not general proof. | 8 emails × 5 versions: the instruction at the start flagged 24 of 24 times, at the end 5 of 8. |
| **Capability probe** | képességpróba | A small, isolated experiment to find out whether a solution pattern works and where it fails. A successful probe on synthetic examples does not yet prove the accuracy to be expected on real business data. | We test three-level matching on six synthetic pairs. |
| **Derived counterexample** | származtatott ellenpélda | A separately marked synthetic variant made from a real source to try out a specific error. The original document stays unchanged. | A test sentence added at the end of the document withdraws the earlier amount. |
| **Group-held-out sample** | csoportosan visszatartott minta | Related emails go together either into development or into the later check, so that the same thread does not produce a misleadingly good result. | Emails from the same sender or with the same attachment stay together. |
