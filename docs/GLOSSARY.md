# Glossary

The shared dictionary of the project: every technical term used in the code, the documentation and the user interface, explained in everyday words, together with its Hungarian equivalent.

## Plain-language summary

This glossary explains the project's technical terms in everyday language. Each entry gives the English term, the Hungarian word used in the Hungarian interface and in conversations with the owner, a short meaning and an example. The terms are grouped by topic: the building blocks of the system, work packages and runs, review, results, documents, the AI components, email, measurement, operations and the development process. It is the only dictionary of the project, so every summary, handoff and README section builds on these definitions.

## How to use this glossary

- **Add first, then use.** A new term goes into this glossary before it appears in any text. On its first use in a text, explain it in half a sentence or link here ([CLAUDE.md §8](../CLAUDE.md), [documentation standard](guides/DOCUMENTATION.md)).
- **Hungarian column.** The owner works in Hungarian and the interface shows Hungarian by default, so every entry carries its Hungarian word: use that word in Hungarian text and in conversation. Older or alternative names follow in parentheses.
- **Interface labels** are quoted with their label from the English interface (for example Approve and release); the Hungarian label is in the Hungarian column or in parentheses.
- **Document vocabulary.** Hungarian text printed on documents (for example "fizetési határidő", payment due date) is quoted in Hungarian with an English gloss, because the code and the models match on it.
- **Numbers** use the en-GB format (decimal point); values quoted from documents keep their printed form (for example "54.732 Ft").
- **Origin tags.** A tag at the end of a meaning names the development session that introduced the term: "(since 040)" means session 040, and "K1", "K5.3" and so on are stages within a session; a date means the term dates from that day. "(planned in 070)" marks a concept that was planned but not yet built. "(defined in 071)" marks terms that had long been in use but were first defined during the documentation completeness review of 2026-09-30 (071).

## System building blocks

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Framework** | keretrendszer | The shared layer every flow sits on: the JEV caller, the config files, the decision rules, measurement and storage. The goal is to assemble a new flow from it rather than build one from scratch. | A German invoice flow uses the same framework as the Hungarian one. |
| **Flow** | flow (folyamat) | The sequence of steps a document or email passes through: reading → questions to JEV → decision → saving. The three reference flows are invoice data extraction (M2), document type recognition (M1) and email intent (M3); two experimental learning branches run alongside them. | A PDF arrives → at the end we know its type, and it has been saved. |
| **M1 / M2 / M3** | M1 / M2 / M3 | Short names of the three reference flows: M1 is document type recognition, M2 is data extraction (starting with invoices), M3 is email intent recognition. We measure the quality of the framework on them. (defined in 071) | "The S path of M2" = the invoice data extraction path in which code searches for candidates. |
| **Burr** | Burr | The library that runs the flows: it describes the steps and transitions as a graph and logs every run. | The flow diagrams in the documentation are generated from it. |
| **Pydantic AI** | Pydantic AI | A library for describing up front the structure of the result expected from the AI, and then calling the model with it; besides generative models it also supports JEV. A correct structure does not guarantee a true answer. | The language is one of the listed options; the yes-probability is a number between 0 and 1. |
| **Adapter** | adapter | The single gateway to JEV. It remembers earlier answers (cache), logs every call and its cost, retries on errors and, when JEV is unavailable, puts the case in the manual queue instead of failing the flow. | The same question asked a second time: 0 HUF, instant answer. |
| **Call site** | hívási hely | A specific point in a flow where JEV is asked, with its own question set and config file. Families: type recognition (broad and detailed), email intent, field selection (Hungarian, foreign and utility invoices) and verification (per type); each has its own config file. | The "invoice field selection" call site sends three question packages per invoice. |
| **Store** | adattár | The local database (SQLite) holding the processed documents, extracted data, emails, the items awaiting manual review and the call log (ledger). The interface calls it the database (for example Database backup). | The types of the 913 PDFs are stored here. |
| **Ledger** | ledger (hívás-napló) | The store table with one row for every JEV and GPT call: when, which step, how many tokens, what it cost, whether it came from the cache, whether it failed. See also call log. | Today's cost is read from here. |
| **Local service** | helyi szolgáltatás | The shared gateway to the framework for the interface and the command line: a program that accepts requests only from the same machine. It rejects requests from other machines or from foreign web pages, and lets only requests with a validated structure and a bounded size through to processing. The technical term is API. (since 040 K2) | The `serve` command or `scripts\dev.ps1 start`; address `http://127.0.0.1:8930`. |
| **Endpoint and endpoint list** | végpont és végpontlista | An address of the local service that the interface or a program calls (for example the health endpoint). The endpoint list is the machine-readable description of every address (`/api/openapi.json`). (defined in 071) | `/api/health` |
| **Fingerprint (hash)** | ujjlenyomat (hash) | A short identifier computed from the content of a file or text: if the content changes by a single letter, the fingerprint changes. It shows whether a document or config file has changed, and it lets a value appear on a list without its readable form. (defined in 071) | The config file's fingerprint in the call log. |
| **Run-bound response log** | futáshoz kötött válasznapló | A copy of the actual requests and responses of one processing run, kept in order. Earlier decisions can be replayed exactly from it. The shared cache, by contrast, may hold a later answer to the same request, so on its own it does not prove what happened in the earlier run. (since 2026-09-21) | — |

## Work packages and runs

### Work packages

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Work package** | munkacsomag | A group of documents and emails from one source (folder, upload, mailbox) that are handled together. A recipe is assigned to it, and it can have several runs. The concept comes from the legacy AIFLOW V4. (since 040) | "September utility bills": 14 PDFs from one folder. |
| **Work item** | munka / munkatétel | A document or email to be handled, with a stable identifier; it can have several processing runs. (since 039) | An invoice awaiting correction in the Work items (Munkák) view. |
| **Work folder / watched folder** | munkamappa / figyelt mappa | A folder set in Settings that the worker checks at intervals: new PDFs become a work package (one shared package, or one per day). The folder is only read; the package gets the recipe, but no paid run starts on its own. (since 057) | "Incoming invoices", daily packages, checked every hour. |
| **Hidden (archived) work package** | elrejtett (archivált) munkacsomag | A package taken off the list. Its runs, call log and results are kept, it can still be opened directly, and the list shows it again with the Hidden packages too filter. A watched folder does not add new documents to a hidden package; it starts a new one instead. Only a package that never had a run (it may still contain documents) can be deleted permanently, after confirmation; the fact of the deletion stays in the log. (since 058) | A test package created twice by mistake, with 0 documents, can be deleted; the package of a closed measurement can be hidden. |
| **Work package owner** | csomag felelőse | The person from the Users list assigned to the work package. The Only my work packages filter uses it to show one's own packages. It is not a permission: others can work on the package too. (since 061) | The owner of the September utility package is Teszt Elek. |

### Recipes and runs

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Recipe** | recept (folyamatrecept) | A versioned description of a task's input, steps, output and settings. (since 039) | Read → extract → check → export. |
| **Processing profile** | feldolgozási profil | The concrete model, OCR and verification settings used for a recipe. (since 039) | GPT extraction and an optional JEV flag. |
| **Configuration snapshot** | konfigurációs pillanatkép | An unchanged copy of the settings used at run time; later edits do not change it. (since 039) | The same document later gets a separate run with a new profile. |
| **Run** | futtatás / futás | Running a recipe on the fixed input of a work package, tracked and with a capped cost. It is either a trial run (changes no business data) or a live run (valid after approval). (since 040) | A trial run of the invoice recipe on the September package: 14 items, 3 to-dos, 0.02 USD. |
| **Trial run and live run** | próbafutás és éles futás | The result of a trial run can only be viewed. A live run is approved by a person (Approve and release), and only when every item has finished and no to-do is open. (since 040 K1) | First a trial with the new recipe, then a live run and approval. |
| **Readiness check** | készenlét-ellenőrzés | A check before a run: is every required input present, and what needs attention. (since 040) | The warning "2 PDFs have no text layer, OCR needed". |
| **Fixed input** | rögzített bemenet | When a run starts, the items of the work package and their content hashes are recorded. If a file changes afterwards, the worker does not process it but reports an error. (since 040 K1) | An invoice PDF was replaced after the start: the item gets a "source changed" error. |
| **Confirmation page** | megerősítő oldal | The trial run, live run and rerun buttons do not start anything straight away; they lead to a summary page: mode, package, recipe, number of items, highest possible cost. A run can only be started from there. (since 061) | "Confirm starting a live run: 49 items, OpenAI at most 0.59 USD." |
| **Rerun** | újrafuttatás | Repeating a finished run on the same input. Pressing the button twice still starts only one new run; a run in progress cannot be repeated. (since 057) | After a failed run: fix the OCR, then rerun. |
| **Idempotent start** | idempotens indítás | Starting the same run twice on the same input creates only one run; the second request returns the existing one. (defined in 071) | A double click on the Run button. |

### The worker

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Job queue** | munkasor | A durable task list in the store. Every item to be run is one row with a unique key, so the same item cannot be queued twice. The attempt count survives a restart. (since 040 K1) | The 14-invoice run gives 14 rows; a faulty PDF becomes "dead" after two attempts, and the rest keep running. |
| **Worker** | feldolgozó | The background program that takes the items from the job queue one by one and runs them. Only one runs at a time; since K2 a lock guards this, and a second instance does not even start. On request it exits cleanly after the item in progress. (since 040 K1) | The `worker` command; on start-up it puts back into the queue whatever an earlier stop left half-done. |
| **Orphaned task** | félbemaradt (árva) feladat | The worker was working on an item when it stopped (machine restart, forced stop, crash). On start-up the task goes back into the queue, behind the fresh work. If the same task is left half-done three times, it counts as dead and the item is marked failed, so that it does not bring the worker down again and again. If someone requested a stop while the worker was down, the task is closed as stopped on start-up. (since 063) | A damaged PDF "kills" the worker three times: on the fourth start the item is failed and the other items run. |
| **State store and thinning** | folyamatállapot-tár és ritkítása | After every step the worker saves the full state of the flow, so that it can resume from there after a stop. For a finished item only the last save is needed, so the others are deleted (thinning); compaction then returns the freed space to the disk. (since 064) | 991 flows: about 108 MB instead of 703 MB. |

### Cost and budgets

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Budget** | keret (költségkeret) | The cost limit of a run, per provider (OpenAI and JEV): the sum of its per-item cost budgets. Every paid call reserves from it first (cost reservation); the owner's overall budget and sub-budgets sit above it. In Hungarian "keret" also means a box on the page image; the context tells which is meant. | A run with a 1.00 USD budget. |
| **Call log** | hívásnapló | For every paid model call (GPT, JEV) an entry is written BEFORE the call and completed afterwards with the actual model and cost. Failed calls are included. (since 040 K1) | A timeout is a "failed" entry with an unknown cost; the budget counts it at the highest possible amount. |
| **Cost reservation (budget reservation)** | költségfoglalás, más néven keretfoglalás | Before a call, an upper bound of its cost is reserved from the run's budget. Since 075 it is a real bound, not an estimate: at most one token per byte of everything sent, plus a fixed overhead, for every possible retry. If it does not fit, the call does not start; if a call still costs more, the run makes no further call with that provider. With a known cost the unused part is released; with an unknown cost it stays reserved. (since 040 K1) | With a 1.00 USD budget, after 0.99 USD a call that may cost up to 0.20 USD no longer starts. |
| **Sub-budget** | részkeret | A cost limit for a particular measurement or trial, approved in advance by the owner within the overall budget (OpenAI and JEV separately; the amount is in the decisions log, which is internal). A new decision is needed before it is exceeded; old sub-budgets cannot be merged. (since 066) | "0.35 USD of JEV for the v1.0.2 re-measurement" (066). |
| **Per-item cost budget** | tételenkénti költségkeret | The maximum amount the system reserves per item (document, email, attachment) and per provider when a run starts. The run's total budget is the sum of the item budgets. It is an upper limit: the actual cost is usually lower and can be followed on the run's page. The budget depends on the chosen path and the settings (for example, task proposals, when switched on, add an extra amount per email). (since 063) | Invoice, G path: JEV at most 0.05 USD, OpenAI at most 0.10 USD per item. |
| **Uncertain attempt** | bizonytalan kísérlet | A paid call of which we do not know whether it went through, for example because the program stopped in the meantime. It is not repeated automatically, because we would pay twice; it has to be settled by hand. (since 040 K1) | A stop after the GPT response but before saving. |

## Review and correction

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **To-do** | teendő | A reason on an item that calls for human review. To-dos can be resolved reason by reason; closing one reason does not close another. (since 040) | "The invoice total does not match the sum of the line items." |
| **Review queue (manual queue)** | review-sor (kézi sor) | The store's list of the cases that the rules say a person has to look at, with the reasons. | "Uncertain type, 0.45" |
| **Review reason** | review-ok | A short machine code saying why a case went to the manual queue; a case can have several; once written it is never removed (the process can only become stricter). | "Uncertain field: bank account 0.56" |
| **Earlier to-do** | korábbi teendő | An open to-do on a document that was raised not by the run being viewed but by an earlier measurement or run. It is shown, but it does not block the current run's status or approval. If the current run raises the same reason: for a trial run, the reason moves over to it; a reason belonging to a live run that has not been approved yet stays where it is, and the current run gets its own row (066), so the earlier live run cannot be approved without review either. (since 040 K3) | An "uncertain bank account number" to-do from an old measurement, on an invoice that has just run without errors. |
| **Field correction** | mezőjavítás | A field value corrected by a person on an item of a run. The machine-extracted data stays unchanged next to it; the corrections form a separate, versioned series. If someone else has saved in the meantime, the save is rejected (no silent overwrite). (since 040 K2) | The invoice number is corrected from "MINTA-1" to "MINTA-1/A"; the report shows the corrected value, and the machine value can still be traced. |
| **Working copy** | munkapéldány | What the user has typed into a correction but not yet saved. If saving fails (no connection, or someone else saved in the meantime), the working copy is kept, so nothing has to be typed again. (since 040 K3) | After a network error, the typed invoice number "MINTA-1/A" is still in the field. |
| **Version conflict** | verzióütközés | Two saves of the same data, where the second would build on an older state: the service rejects it (409) and asks for a reload. This way one correction never silently overwrites another. (defined in 071) | The same field correction in two browser tabs. |
| **Page image** | oldalkép | The image of one page of a document in the interface, on which the boxes of the fields found are drawn. The service renders it anew for every request; since 071 the browser does not store it. (defined in 071) | The image of page 1 at 144 dpi. |
| **Source location** | forráshely | Where an extracted value stands on the document: page, box, the printed text. If it is ambiguous, there is no box, only an explanation. (since 045) | The box of the gross amount next to the label "Bruttó összeg:" (gross amount). |
| **Confidence band** | bizonyosság-sáv | The model's estimate shown in three colour-coded bands: Confident (≥ 90%, green), To check (50–89%, blue), Likely wrong (< 50%, red). Display only, not a decision threshold. (since 045) | A bank account number at 58% with a blue marker. |
| **No estimate (field without candidates)** | nincs becslés (jelölt nélküli mező) | If the code finds no candidate for a field, JEV does not choose, so the field has no confidence; the interface shows No estimate (before 2026-09-29 it wrongly showed Confident). For important optional fields we ask JEV whether the value is on the document at all; if it is, a to-do is raised. | The card-paid foreign invoice has no IBAN candidate, and according to JEV there is no IBAN on it either: no to-do. |
| **Alternative candidate** | alternatív jelölt | The other values considered for a field, shown on the image with a dashed box and the model's estimated probability. One click makes it the field's value (as a correction, with an author). (since 045) | Next to the net amount, "10 000" at 8%. |
| **Selection on the image** | kijelölés a képen | The reviewer clicks words on the image or drags a rectangle; the system interprets the selected text according to the field's kind and saves it together with its location. (since 045) | Selecting an IBAN broken over two lines. |
| **Approximate box** | közelítő keret | A dashed box on the line from which the machine picked the value, used when the exact words cannot be found on the document. A field under review is thus never left without a location; the exact location can be added by selection. (since 046) | The line "1117, Budapest" when the address appears in a different form on the document. |
| **Value in several places** | több helyen szereplő érték | If a field's value appears verbatim in several places on the document (for example the invoice number at the top and on the payment slip), the box goes to the most likely place: next to the field's own label or, failing that, the first occurrence. The other places are dashed, clickable alternatives. (since 053) | "Appears in 2 places in the document; the box is on the most likely one, the others are dashed." |
| **Line-item location** | tételsor helye | The box of one row of a line list on the image. The system finds it in the word layer from the row's amounts and dates, in code. If only part of the row's data can be found, the box is approximate (dashed). (since 053) | Clicking the 2nd line item makes the image jump to the invoice details page, and the row gets a green box. |

## Documents and extraction

### Document types and type packs

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Registry** | regiszter | The list of recognisable document types (12 + "unknown") and of email intents (11), each with a description: what it is, what it is NOT, examples, and which family it belongs to. JEV receives this description as its options. | "Hungarian invoice" (magyar számla): issuer with a Hungarian tax number, forint, "fizetési határidő" (payment due date). |
| **Parent family** | szülő-család | A group of types in the registry (for example every invoice-like document forms one family). If the exact type is uncertain but the family is certain, we report that. | "I don't know whether it is a Hungarian or a foreign invoice, but it is an invoice." |
| **Detailed type** | részletes típus | The exact document type within a broad recognition category, with its own type pack: for example the CIB statement within the "bank statement" category. It decides which fields are extracted. (since 047) | "utility invoice" → "sewerage fee invoice" (közmű-számla → csatornadíj-számla) |
| **Anchor score** | horgony-pontszám | The legacy system's keyword-based confirming score: required keyword 1 point, supporting word +0.25, excluding pattern −0.5 (between 0 and 2). If one detailed type clearly leads, the code decides; otherwise JEV chooses. (since 047) | "Csatornázási Művek" (sewerage works) + "szennyvíz" (waste water) → the sewerage fee invoice leads. |
| **Type pack** | típuscsomag (típus-csomag) | All type-specific data of a document type (for example Hungarian invoice, foreign invoice) in one config file: the fields and their kinds (name, tax number, date, amount, currency, country…), which field is scored, required or high-stakes, which checks run, the legacy extraction prompt and schema, and the names of the JEV question sets. | Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Text layer** | szövegréteg | The copyable text stored in a PDF. PDFs from invoicing software have one; scanned (photographed) invoices do not, and there the PDF is only an image. (since 2026-09-20) | The 49 legacy utility golden documents are all images without a text layer. |
| **Word layer** | szóréteg | All the words of a document with their positions on the page, as the run read them. The boxes are drawn from it; no AI call is needed. (since 045) | "12 700" is two words in line 3, on the right half of the page. |

(since 065) | An invoice number of the form "AB12CD34-0009" used to come out in two pieces ("AB12CD34" and "0009"). |
| **Protected line boundary** | védett sorhatár | A page or structural boundary across which the program does not allow lines to be joined. (since 2026-09-21) | — |
| **OCR (optical character recognition)** | OCR (optikai karakterfelismerés) | A program that "reads" the letters and digits in an image and turns them into text. (since 2026-09-20) | "54.732 Ft" read correctly, but "Féldgazhalozati" instead of "Földgázhálózati" (gas network). |
| **OCR pipeline** | OCR-lánc | The chain of steps: the pages of the PDF are rendered as images (300 dots per inch), OCR runs on the image (tesseract, with the Hungarian + English language packs), and from the positions of the recognised words we build lines and column cells just as for a PDF with a text layer. From there on, the flow does not know that it received OCR text. (since 2026-09-20) | A 4-page electricity bill takes about 30 seconds. |
| **Native OCR / Docker OCR** | natív OCR / Docker-OCR | Native = the tesseract program installed on the machine (fast, 7–10 s per page). (since 2026-09-20) | The first trial via Docker took 3.5 minutes per page. |
| **OCR confidence (word confidence)** | OCR-bizalom (szó-bizalom) | OCR gives every recognised word a number between 0 and 100: how sure it is. The average (stored on a 0–1 scale) and the share of weak words (below 60) are the document's OCR quality signal; the threshold is in the config file, and below it the document goes to the manual queue. (since 2026-09-20) | Electricity bill: average 0.87, weak words 11%. |
| **OCR cache** | OCR-gyorsítótár | A document's recognised text is written to disk (the key is the file's fingerprint + the OCR settings + the tesseract version). The second time, the same document runs instantly, without OCR. That is why golden measurements are slow only the first time. (since 2026-09-20) | 49 utility golden documents: 15 minutes the first time, 0 afterwards. |
| **Azure Document Intelligence (Azure DI)** | Azure Document Intelligence (Azure DI) | Microsoft's cloud OCR service: we send the image and get back text and word coordinates, much more accurately than with the local tesseract (0.985 word confidence instead of 0.87 in the trial), but it is paid per page and draws on the legacy sidecar's 1000-page allowance. Here it is reached through the legacy sidecar, in two ways: OCR escalation (below) calls it automatically, and a measurement can force it with `JAV_OCR_ENGINE=azure_di`; the `auto` engine choice never picks it. (since 2026-09-20) | A 4-page electricity bill: 12 seconds, 19/19 fields. |
| **OCR escalation** | OCR-eszkaláció | Two-stage OCR: the free local tesseract runs first, and the paid Azure service is called only if the local result is weak (the average word confidence or the share of weak words falls outside the threshold in the config file). The decision is data, not code; the raw run shows when escalation happened. Escalation is switched on in `configs/ocr.json` and runs automatically, but only if the legacy sidecar is running and can reach the file; otherwise the local result stays. Azure calls do not yet go through the call log or a run budget (planned: the Azure recipe option). (since 2026-09-20) | 49 utility golden documents: at the threshold (0.90 / 10%) most of them escalate. |

## AI components

### Models and extraction paths

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **JEV** | Jev (JEV) | TypeSafe's AI model, which does not write text but **gives decision signals for closed questions**. It does not generate new values, but it can pick the wrong one of the options offered. The signal is not the probability that the whole document is correct; time and cost are measured on our own samples. | "Is this number the supplier's tax number?" → a yes-signal of 0.97 |
| **S path and G path (S arm and G arm)** | S-út és G-út (régebben S-kar és G-kar) | The two ways of extracting invoice data. **S path**: code finds the possible values, JEV chooses among them. **G path**: a text-generating model (GPT) extracts the data, and JEV verifies it field by field. Currently the two paths decide separately; an agreement gate between them is only planned. S arm and G arm are older names for the same thing; the interface and the newer reports say S path and G path. | S path: "which of the 9 numbers found is the gross amount?" |
| **Recommended path / automatic path** | ajánlott út / automatikus út | The type pack can say which path the extraction takes by default: code + JEV (S) or GPT + JEV (G). The recipe's automatic setting follows it; an explicit request for S or G takes precedence. (since 053) | Utility invoice: G, because one GPT call gives both the header data and the line items; Hungarian invoice: S. |
| **Second opinion, path escalation** | második vélemény, út-eszkaláció | Every document goes down the cheaper S path; the G path runs a second time only on those where a to-do remains, just as Azure follows the local OCR. This way the more expensive path only touches the difficult documents. (planned in 065) | On the 20 difficult foreign invoices the G path left 12 to-dos instead of 34, at three times the cost. |

### JEV question kinds

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Choice** | Choice (választás) | "Which of the listed options is it?" — JEV gives a probability for every option and picks the most likely one. There is always a "none / unknown / other" option. At most 255 options. | Document type out of 13 options. |
| **Noul** | Noul (igen/nem) | "Is this statement true?" — a single number between 0 and 1: the probability of "yes". | "Is the issuer a Hungarian company?" → 0.97 |
| **Score** | Score (fokozat) | "Where is this on a scale?" — 2–10 levels, each described by a concrete situation (not "medium" but "reminder, deadline within a few days"); meant for degrees (urgency, severity), not for yes/no. The answer: a probability for every level, the most likely level, and an expected value (the probability-weighted average of the levels). We use it for email urgency (since 2026-09-20). | Urgency: 0 no time pressure … 3 final demand; expected value 1.8 = around level 2. |
| **Criterion** | kritérium | The description of a Choice option that JEV reads: what it is (what), what it is NOT (not_for), examples. Accuracy depends on it. | "Hungarian invoice: … NOT: a foreign issuer with a Hungarian buyer" |
| **Instruction** | instrukció | The text of the question, in English (JEV is most accurate in English); the document text, however, is sent in its original language. | "Which value is the SUPPLIER's tax number?" |
| **State** | állapot (state) | The data package sent with the question: selected lines of the document and signals computed in code. Only what the question uses goes into it. | The first 40 and the last 8 lines of the invoice. |
| **Presence question** | jelenlét-kérdés | A Noul next to every field selection: "is this field on the document at all?" This way JEV does not confidently pick a wrong value when the field is missing. | "Is there an IBAN or bank account number on the invoice?" |
| **Batched request** | kötegelt kérés | Several questions in one call on the same state; JEV evaluates them in parallel, and they do not see each other's answers. The shared text is given once, but the questions also consume tokens and cost. | 6 field selections + 6 presence questions in one request. |
| **Structured question (structured instruction)** | szerkezetes kérdés (strukturált instrukció) | The question is not one glued-together sentence but a labelled package, with separate slots for the field's meaning, the extracted value, the lines where the value appears, and the question itself. The JEV documentation recommends this when part of the question is produced by code (for example the same question for every field, only the value differs). | "field: supplier tax number · extracted: 12345678-1-42 · line: L02 · question: is this a different kind of number?" |
| **Verification question (error flag)** | ellenőrző kérdés (hiba-flag) | The second step of the G path: yes/no questions for every field of the generated extraction about whether it is wrong (another field's value ended up here; truncated; a different kind of number; wrongly empty; parties swapped; a missing line item). "Yes" means an error; above the yes band the case goes to the manual queue. | "Is the supplier name truncated?" → 0.97 → manual queue |
| **Source localisation (finding the source location)** | forráslokalizálás / forráshely keresése | Determining on which page, line or text block the data sought is found. It is not guessing the value itself: the code copies it from the original source. | Selecting the line that contains the invoice number. |
| **Structure recovery** | szerkezet helyreállítása | Recognising the lines and text parts that belong together: header, item, summary. The original text is kept; only the grouping changes. | Attaching a product name broken over two lines to one item. |
| **Source-based verification** | forrásalapú ellenőrzés | Comparing an extracted claim with the original text: the source supports it, contradicts it, or does not discuss it. | The number is on the page, but it belongs to the buyer, not to the supplier. |
| **Request-size budget** | kérés-méret keret | JEV accepts only a limited amount of text per request (beyond it, it returns a "max_tokens_exceeded" error). The call site's setting: if the request is too large, the code first narrows the text to the candidates' lines, then shortens the option descriptions, and finally reduces the number of candidates — in document order, so that the parties at the top of the invoice are not dropped. The same applies on the verification path: only the evidence lines are sent instead of the full text. The budget is measured in characters and JEV counts tokens, so an overflow can happen even under the budget: the code then retries once with a narrower question and gives up only after that (manual queue). The reduction is visible in the raw run. (since 2026-09-20) | The 9-page Díjbeszedő bundle: 40 of the 92 name candidates fitted. |

### Decisions and thresholds

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Confidence** | confidence (magabiztosság) | For a Choice: how concentrated the probability is on one option (0–1). It is not the same as the probability of the most likely option, but close to it. | 0.99 = almost certain |
| **Band** | sáv | Splitting the raw probability into ranges for the decision. For a yes/no question: no (< 0.30) / uncertain / yes (≥ 0.70). For a choice: automatic (confident) / uncertain (the second option is too close) / manual (below the threshold, currently 0.60). The thresholds live in config files, not in code. | 0.45 confidence → manual band |
| **Second-option gap** | második-lehetőség rés | The difference between the probabilities of the most likely and the second option; if it is small (< 0.20), the choice falls into the uncertain band. | 0.55 vs 0.45 → gap 0.10 |
| **Threshold** | küszöb | The boundary of a band. It can only be changed in the config file, with a version number; after a change, old runs can be re-evaluated without calls. | Manual band boundary 0.60; 0.85 for high-stakes fields. |
| **High-stakes field** | magas tétű mező | A field where an error is expensive (amount payable, due date, bank account, tax number): the threshold is higher here. | A gross amount at 0.84 is still manual. |
| **Route** | útvonal (route) | Where the case goes after the decision: automatic acceptance, manual queue, another flow, archive. It is decided in code from JEV's answers; JEV does not choose it. | "Invoice sending" intent + PDF → the type recognition flow |
| **Record confidence** | rekord-confidence | The reliability of a whole extracted invoice: its weakest field judgement. Currently it is only recorded and does not affect the route. | 0.53, because the bank account judgement is weak. |
| **Parent label** | szülő-címke | If the exact type is uncertain but the probability of the parent family reaches the threshold (0.85), the family is given to the manual reviewer as the label. | "Invoice-like, exact type in question" |

| **Manual learning candidate** | kézi tanulójelölt | A preserved source, a machine proposal and a later human decision kept together. This does not make it an active capability. (since 031) | A reviewed email can be exported as an example; a separate evaluation and a manual inclusion follow. |

## Measurement and quality

### Golden set and scores

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Golden set** | etalon (etalon-készlet, golden) | Hand-checked, "certainly correct" examples: invoices with every field (for example 12 Hungarian invoices), documents with their type, and emails with their intent. Current sizes and results are in the state snapshot (`docs/STATE.md`, local). The system is measured against them. They stay in the legacy project because they contain personal data. | "The 144 fields of the 12 invoices" |
| **Accuracy** | pontosság | The share of correct answers on the golden examples. Always give the count next to the percentage. | 144/144 = 100% |
| **Candidate recall** | jelölt-lefedettség (recall, jelölt-recall) | The part of the golden values that can be found among the candidates collected by code. JEV can only choose from candidates, so this is the best result the S path can reach. It can be measured without AI calls, for free: `python -m jav.cli recall`. | 144/144: all 144 values of the 12 Hungarian golden invoices are among the candidates (065). |
| **Coverage of selected fields** | kijelölt mezők lefedettsége | How many of a predefined set of data items the system found in the right role. It says something only about those fields. (since 030) | 16 requested values appeared; the completeness of the other fields is unknown. |
| **Presence truth** | jelenlét-igazság | The golden reference for the presence question: whether the field is filled in according to the golden set. | One invoice has no bank account → "no" is the correct answer. |
| **OCR-tolerant match** | OCR-tűrő egyezés | A second, informative score in the golden measurement: names, addresses and text are also compared without accents, case and punctuation. The difference between the strict and the OCR-tolerant figure is what only the OCR's accent noise spoiled. (since 2026-09-20) | mohu: strict 88.7%, OCR-tolerant 93.3% |
| **Calibration** | kalibráció | Whether what JEV says about its own certainty is true: are its 90% answers really correct 90% of the time? One number for the deviation is the ECE (0 = perfect). | ECE 0.01 = very well calibrated |
| **Determinism measurement** | determinizmus-mérés | Asking the same question several times without the cache, and checking whether the answer changes (a label change = flip) and how much the probability fluctuates. | 12 invoices × 3 runs: 0 flips |
| **Cache** | gyorsítótár (cache) | The adapter stores the answer for every (model version + state + questions) triple; asking the same question again is free. Any change to a question or description gives a new key, and so a new live call. | Rerunning the golden set costs 0 HUF if nothing has changed. |
| **In-sample (measured on the training examples)** | a tanító példákon mért (in-sample) | When a rule is tuned on exactly the examples that are then used for measuring — a good result is then not evidence, only a signal. This must always be stated. | 96/96 after a sentence tailored to one email. |
| **Raw run** | nyers futás | The complete, row-by-row result of every measurement, in a file; the report is built from it, and it can be re-evaluated without calls. | Every number in the report can be traced back. |
| **Eval report** | eval-riport | A one-click summary of the raw runs: accuracy per question, bands, calibration, how many cases would change band after a threshold change, determinism. | "How many cases would go to the manual queue if we tightened it" |
| **Verifier probe** | ellenőrző-szonda | Measuring the verification questions without generative calls: JEV gets the correct golden extraction (on which it must flag nothing) and deliberately broken variants of it (parties swapped, truncated name, empty invoice number, gross instead of net, phone number as tax number), on which the matching error flag must fire. The result per band: how many broken variants fell into the yes, the uncertain and the no band. | 12 invoices × 4–6 variants = 52 runs |
| **Capability probe** | képességpróba | A small, isolated experiment to find out whether a solution pattern works and where it fails. A successful probe on synthetic examples does not yet prove the accuracy to be expected on real business data. | We test three-level matching on six synthetic pairs. |
| **Derived counterexample** | származtatott ellenpélda | A separately marked synthetic variant made from a real source to try out a specific error. The original document stays unchanged. (since 030) | A test sentence added at the end of the document withdraws the earlier amount. |
| **Group-held-out sample** | csoportosan visszatartott minta | Related emails go together either into development or into the later check, so that the same thread does not produce a misleadingly good result. (since 031) | Emails from the same sender or with the same attachment stay together. |

### Comparing models

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Agreement filter** | egyezési szűrő | Code compares the decisions of two separate models and flags uncertainty when they differ. Agreement alone does not prove the truth either. (since 035) | GPT says copy, JEV says correction: manual review. |
| **Same-decision-output control** | azonos döntési kimenetű kontroll | The models being compared are asked for the same decision task, so that extra work asked of one of them does not distort the cost difference. (since 035) | Both give only the relationship type; neither is asked for a long justification that the other is not asked for. |
| **Independent model judgement** | önálló modellítélet | The model evaluates the source without the other model's answer. The errors of the two models may still be correlated. (since 032) | OpenAI and JEV interpret the withdrawal of the deadline separately. |

## Operations and security

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Operations log** | üzemi napló | The permanent log files of the local service and the worker (`runs/logs/api.log`, `runs/logs/worker.log`). Every unexpected error is written here with its full traceback, together with the worker's starts and stops. The file rotates every 5 MB, and 5 old copies are kept. (since 063) | "Why did the worker stop overnight?" — the last lines of worker.log tell you. |
| **Store backup** | adattár-mentés | A verified copy of the store (work packages, runs, corrections, decisions), made even while the system is running. Since 2026-09-29 it runs automatically every day at 12:00 (Windows Task Scheduler), and a copy verified by content hash also goes to the network storage; the latest 14 are kept in both places. The status of the latest backup is shown on the Settings › System page (as Database backup); a backup that is too old or has failed triggers a warning. Restoring is manual, with the service stopped. (since 063, 064) | "Last backup: today 12:00, OK; copy on the NAS: verified." |
| **Second backup location (NAS)** | második mentési hely (NAS) | Where the verified copy of the daily backup is kept outside the machine; for the author, a network storage device (NAS). On another machine, set your own location in the config file. (defined in 071) | The latest 14 backups in both places. |
| **Release version** | kiadási verzió | A code state marked as stable by the owner, with a numbered git tag (`v1.0.0`) and release notes. It is always possible to go back to it. The `v1.0.0`–`v1.0.4` tags exist only in the local, archived history; on the new line (and on GitHub) `v1.0.5` is the first. Stage-end markers (for example `felulet-062-kesz`) only mark development steps; the release version marks the state recommended for use. (since 063) | `v1.0.0`: the first stable version, 2026-09-29. |
| **Input limits** | bemeneti korlát | Upper limits on a document's file size, page count and page image pixel count (`configs/service.json`), so that a huge document cannot exhaust the machine; above them the item stops with a named error or gets a to-do. (since 067) | 100 MB, 300 pages, 40 megapixels |
| **Browser security header** | böngészős védőfejléc | An instruction to the browser attached to the local service's responses, for example: the interface cannot be embedded in another page, it may only load its own files, and it does not put personal data into its disk cache. A second layer behind the existing protections. (planned in 070, in operation since 071) | `X-Frame-Options: DENY` |
| **Content security policy (CSP)** | tartalombiztonsági szabály (CSP) | One of the browser security headers: it tells the browser where the interface may load scripts, styles, images and fonts from. Here: only from its own address. (defined in 071) | A script from an external host does not run. |
| **Data guard** | adatőr | A check before commit and push: it looks for patterns of personal data (tax number, bank account, email, phone) or keys in the lines going into git, and stops the operation if it finds one. Invented sample values are on an allow list. Old personal data not yet replaced is a **tolerated known value**: it is on the list only as a fingerprint, and it passes only in the file where it is now. (planned in 070, in operation since 071) | A real-looking bank account number in a test: the commit is rejected. |
| **Language guard** | nyelvi őr | A ratchet in the start-up check: it counts, per tracked file, the lines that contain Hungarian letters and fails if a file has more than its baseline entry (a new file: any). Everything that reaches GitHub is English; Hungarian stays only where it is data (document vocabulary, UI translation files, synthetic test documents). The baseline only shrinks; raising one file needs an explicit acceptance. (since 073) | After a comment-only translation the baseline is lowered with `lang-guard --update`. |
| **Real-looking value** | valódi alakú érték | A tax number, IBAN or bank account number whose check digit is also correct, so it cannot be ruled out that it is real. A value with a wrong check digit is certainly invented; the data guard lets it through. (since 071) | A tax number of the form `NNNNNNNN-N-NN` whose 8th digit matches the weighted sum. |
| **Data inventory and retention period** | adatleltár és megőrzési idő | A list of where personal data is kept on the machine (store, runs, cache, emails, backups, logs), who can see it and how long it stays; after the retention period a thinning command deletes it. (planned in 070) | "Raw runs are kept for 90 days" (an example, not a decision). |
| **Recovery drill** | helyreállítási gyakorlat | A test of whether the working system really comes back from a backup in a separate place, with written steps and a measured time. A successful backup does not prove this. (planned in 070) | "A trial run works from the backup within 20 minutes." |
| **Known vulnerability** | ismert sebezhetőség | A registered security flaw in an external software package; the package list is checked against a public database for these (Python: `pip-audit`, interface: `npm audit`). Since 075 it runs weekly with the daily backup, and the System page shows its date and result. (since 067) | "0 known vulnerabilities in the 70 packages" |

## Development process

| Term | Hungarian | Meaning | Example |
|---|---|---|---|
| **Session** | session (munkamenet) | One working session with Claude; it starts with a status review and ends with a handoff. | This day saw 8 sessions. |
| **Handoff** | átadó (handoff) | A numbered note written at the end of a session: what was built, what was decided, what was measured, what the open question is. The next session starts from it. It begins with a plain-language summary (Laikus összefoglaló). | 008-2026-09-20 |
| **Backlog** | teendőlista (backlog) | The ordered to-do list with status; the order is the priority. | Item 1 = the next piece of work. |
| **Decisions log** | döntésnapló | The owner's decisions with dates; they are not reopened. | "We will not lower the threshold." |
| **State snapshot** | állapot-pillanatkép | A machine-generated page with the current figures (versions, store, latest measurements); it is never edited by hand. | "How many items are waiting for manual review" |
| **Preflight** | preflight | A session-start check in one command: tests, rule checks, config versions, freshness of the handoff. | "151 tests green" |
| **Config as data** | konfig mint adat | Everything that can be tuned (descriptions, questions, thresholds, model names) lives in a config file with a version number, not in code; so a change means editing a file and measuring, not programming. | A threshold change is one line in the file. |
| **Contract** | kontrakt | The declared description of a flow's steps and transitions, which a checker compares with the real program so that the documentation does not drift. | "The flow diagram is always true." |
| **TDD** | TDD | Test first, then code: every change is first expressed as a check. | "151 tests" |
| **Property-based test** | szabályalapú teszt | Instead of pinning down one example, it states a rule ("accepts any valid tax number"), which a library (`hypothesis`) tries on hundreds of generated inputs; on failure it reports the smallest counterexample. (since 067) | "The total stays a candidate whatever line is placed next to it." |
| **Test coverage** | tesztlefedettség | The share of the code's lines that the test suite runs at least once. A high value does not prove correctness, but a low one shows where there are no checks. (since 067) | "91% of the runtime" |
| **Codebase document** | kódtári dokumentum | A lasting description versioned together with the code and published to GitHub: what the system can do, how it is built, how to install and develop it. It changes in the same commit as the code. (since 070) | README, architecture, glossary, guides |
| **Internal working documents** | belső munkaanyag | The local documents of the development process. Git does not track them and they do not go to GitHub; the daily backup copies them (locally and to the NAS). Codebase documents do not link to them. (since 070) | Handoffs, plans, reports, backlog, decisions log |
| **Commit, branch, tag** | commit, ág, címke | Git concepts. (defined in 071) | The `main` branch, the `v1.0.5` tag |
| **Git hook** | git-horog | A program that git runs automatically before an operation and that can stop the operation. Here the data guard runs this way, before commit and push. (defined in 071) | The commit of a test tax number is rejected. |
| **Archive branch and new starting point** | archív ág és új kiindulópont | Only the history after the new starting commit goes to GitHub. | **Adapted port** | illesztett port | Taking over existing business logic with a connection adapted to the new store or interface. (since 039) | Using the legacy export projection without taking over its PostgreSQL query. |
