# Workspace design system

**Plain-language summary.** This guide records how the workspace looks and why, so that every screen follows the same decisions. The interface is a ledger on a desk: warm paper, ink, thin rules, and one wine-red stamp for the main action and the brand. A state (done, running, to-do, failed) is always shown by a small mark in its own colour, never by the action colour, so that what you can do never looks like what has happened. The values below are the tokens in `ui/src/styles.css`; the rules that forbid generic patterns are in section 9 of `CLAUDE.md`.

## 1. Direction

- **Who and what.** A bookkeeper or the owner opens the workspace to see which work packages need them, open the next step and clear to-dos. Later, clients may see it too.
- **Feel.** Dense and calm, like a well-kept ledger: much information per screen, a clear order, and little decoration. The structure stays: a dark side rail, a light canvas, one accent colour.
- **Screens.** Desktop and laptop only, 1366–1920 px wide, mouse and keyboard. Light and dark themes; Hungarian by default, English on request.

## 3. Type, space, shape, depth

- **Typeface.** IBM Plex Sans for text, IBM Plex Mono for codes and identifiers (self-hosted `@fontsource` packages, weights 400, 500, 600 and Mono 400). Amounts, dates and counts use tabular figures in the text face; monospace is not used for amounts.
- **Type scale** (about 1.2 per step): `--fs-xs` 12 px (labels, table headers, metadata) · `--fs-sm` 13 px (the base: body, tables, controls) · `--fs-md` 15 px · `--fs-lg` 18 px (section headings) · `--fs-xl` 22 px (page title) · `--fs-2xl` 28 px (a single large figure). Nothing below 12 px. Hierarchy comes from weight (400, 500, 600) and colour as much as from size; headings use slightly negative tracking and balanced wrapping.
- **Space.** A 4 px grid: `--sp-1` 4 · `--sp-2` 8 · `--sp-3` 12 · `--sp-4` 16 · `--sp-5` 20 · `--sp-6` 24 · `--sp-8` 32 px. Table cells 7 × 8 px; the page gutter 24 px.
- **Radii.** Four values: `--r-sm` 4 px (chips, counts, small markers' frames) · `--r-md` 6 px (buttons, inputs) · `--radius` 10 px (tables, cards, popovers) · `--r-full` (pills and dots). Small state markers are square-cornered.
- **Depth.** Borders carry the structure; only overlays (popovers, menus) get a shadow. No decorative gradients, no glass, no glow.
- **Motion.** Button press scales to 0.97 in 100 ms; colour changes 120 ms; nothing moves on its own. `prefers-reduced-motion` turns transitions off.

## 4. Components

- **Buttons.** `.primary`: solid accent, one per view, for its main action. `.secondary`: paper with a strong hairline border, ink label. `.quiet`: text only. `.small-btn`: 28 px high, 12 px label. All at least 32 px high (28 px for small ones). An editor's save (a field, a correction, a setting, a pairing) is solid only while there is something to save; idle, it is a disabled secondary button, so a calm view shows no faded solid button. A form's main step (create, next, start) stays solid and is disabled until the form is complete. Every button carries a shared class: no bare browser button. `.danger` uses its own ink token, so its label stays readable on the dark theme's light red.
- **Run buttons.** Every button that starts a run — trial, live, rerun — carries the run's cost cap after a thin divider (`.spend`, for example "≤ 1.71 USD", the sum of the services' caps), because a trial calls the same paid services as a live run; the full sentence is in the tooltip and the mark is hidden from screen readers so the button keeps its name. A run that can spend nothing carries no mark. The recommended run is the one solid button; otherwise the live run, whose result can be released, has a firm ink border.
- **State mark** (`.status`, `.s-<state>`). A 7 px mark plus a plain label: done ● green, running ● blue, queued ○ blue ring, to-do ● orange (orange label), failed or cancelled ■ red. The header's worker badge (`.pill`) uses the same marks; a warning is an amber ◆.
- **Attention count** (`.count-alert`). A count above zero of to-dos or runs to supersede: orange figure on its tint, tabular; zero is shown muted (`.count-zero`). 216: the header's "Waiting for me" link carries the person's count after its label, as the "My work today" link's neighbour (`.waiting-link`).
- **Stage track** (`.track`). Three short segments before a package's next step — Processing, Review, Result — filled up to where the package stands; the current segment takes the state's colour (running blue, to-do orange, failed red; all green when released). It is decorative (`aria-hidden`): the step's text says the same in words.
- **Links.** Ink with a quiet underline; accent on hover. In table cells the underline appears on hover only.
- **Language switch.** One segmented control (HU / EN), not two separate buttons.
- **Side rail.** Dark, 120 px; icon above a 12 px label; the current item is a lighter block (no stripe on its side).
- **A package's page.** A compact header (18 px title, the summary and the workflow it belongs to on one small line, the owner and the next step on the right) and the three stages as one 40 px bar: number, name and state on one line; the open stage is a neutral tint with an ink underline.
- **A package's items** (168). The same card in Processing (below the Run card) and in Review. Its first line is a tally of the item states, each a state mark: approved ● green, processed live (its approval a person's turn) ● orange, processed in a trial ○ ink ring, being processed ● blue, failed ■ red, pending ● ink, removed — a dash in muted text. Adding shows its three steps (choose, check, add) as small numbered marks, the current one filled with ink; the preview's rows say what happens to each file (new ● ink, already there ○ faint ring, removed earlier — a dash), and its last step is the view's one solid button while the form is open (the run card's recommended button turns secondary meanwhile). The pending items' line repeats their run button, never as the solid one. Several items are removed from the selection's bar, with one reason. A reconciliation package (169) shows the same card for its inputs: the tally counts statements, invoices, other parties' invoices (muted) and the left-out ones (a dash); adding first names the package the files go to (a plain row above that package's framed add form, no frame of its own).
- **Review workspace.** The run picker has a fixed width and the keyboard help takes the rest of the toolbar row (in full in its tooltip). The panes measure where they start and end just above the bottom of the screen, so on a 1366 × 768 laptop the page image, the first fields and the save button show without scrolling the page. The selected item and the active field are cards with a firm border, never a side stripe.
- **Result section.** One row for the result picker (fixed width, its label for screen readers only), the views and the full Excel package. The picker's first choice, and the default, is the package's current result (each item from the run whose result counts now); the package's runs follow, each showing its own result. Under the row the release line: one line with its own state mark — released ● green, a release a person can give or open to-dos ● orange, a live run still running ● blue, failed ■ red, partly released or changed since the release with nothing to release now an amber ◆, a trial's result neutral — and its detail in muted text; never a tinted banner. Items shown from a trial and items removed from the package are quieter marks on the same line. On the package's result the line ends with Approve and release, the solid main action only when it can be given (a released package shows its latest version's download instead); a run's own line has no approval and leads to the package's result. The released versions are a quiet fold under the line: a compact table of version, who released it, when ("recorded afterwards" in muted text for a version recorded later), items and the stored downloads. A view may hide columns a person seldom reads by default (the column menu shows them, and the full Excel package always has them).
- **Reconciliation.** A line's, an invoice's or a card's state is a state mark before its label (to decide orange, something off an amber ◆, settled green, nothing to do grey), never a coloured side stripe or a tinted pill; the selected row and the focused card have a firm ink border. One solid action per view: on the quick review accepting the sure pairs, on the cards only the focused card's acceptance (the one Enter takes), on the approval only when nothing blocks it. Amounts use tabular figures in the text face; account numbers, as codes, stay in the mono face.
- **Approval of a logic pack's own version** (192). One shared element (`ui/src/components/ApprovalPanel.tsx`) for the reconciliation and the quote: approved, a green notice with the version, who and when, a muted line on what the lock means, an amber notice when the data changed since, and reopening with a required reason (a secondary button that asks once more); not yet, a muted line on what the approval records, "What blocks the approval" with the pack's own list or a green "Nothing blocks the approval", and the approval, the view's one solid button only when nothing blocks it. The reopened versions follow as a plain list, each with what the pack lets a person do with it (a download). Moving the reconciliation onto it changed no pixel of its page. Stage D0 (D0-d): a case step's approval out of date shows an amber notice (`.notice.warn`, which the changed-since notice now uses too, as this rule always said) naming the step whose result changed; a returned one an orange notice (`.notice.todo`: a person's turn) with who, when and why; while it is not approved, "Return it" with a required reason, a secondary button that asks once more, as the reopening. The shared approval element (`ui/src/elements/registry.tsx` `approval`) shows the step's domain's own approval where it registers one (`registerApprovalBody`; the quote's), else the general one (`GeneralApproval`): the state, the earlier versions and the return.
- **An editor's save line and a refused save** (stage D0, D0-g; `ui/src/components/SaveConflict.tsx`). The save line is one muted line in the editor's head: no change, changed, saving, saved with when, not saved, not known. A save refused because someone else saved meanwhile is an amber notice (`.notice.warn`: something is off, the person decides) holding a compact table on the paper colour in ink: what, mine, saved now, with "changed by them too" in muted text under the field's name; then "Keep my changes", the notice's one solid button, and "Drop mine, keep theirs", a secondary button that asks once more. A save whose outcome is not known is the same amber notice with one sentence and a secondary "Save again". An approval that waits for unsaved work lists it first among what blocks it, in the to-do colour, with a link to the editor. Stage D (D-a): while anything is not saved, the editor's head mark is the to-do "save the changes first", never the green "ready to approve"; a change to a removed row says so in muted text under its name.
- **Quote editor** (192, `ui/src/domains/quotes/QuoteEditor.tsx`). The request is a narrow reference column (272 px, scrolling on its own within the screen): its requested items first, each with a small square number, then its data. The quote is the working area: a one-line header summary between two hairlines that opens into the header fields (open while the customer is missing), then the lines. Each line carries the requested item's number (on the to-do tint while something holds it), the item picker, its state mark (sure green, to check orange with its "Confirm the item" button beside it, not in the list an amber diamond, confirmed green with who), the item code in the mono face and "Asked: …" in muted text; what still holds the line is a line of to-do text under it. Prices and discounts show as values in ink; a price of a person's own says so under it; a note row opens for an own price. The totals close the lines like a ledger: net and VAT in muted labels, the gross total 22 px semibold under a double rule. Every change is saved at once (the head's save line says no change, changed, saving, saved with when, not saved, or not known: the shared save behaviour below); an error shows under the head. The page header's next step is the view's one solid action; the card's "To the approval" stays secondary. A mark with a sentence wraps (`.status.long`).
- **What an email may start** (192; 231 C1a general). Below the email's intent and next step, after a hairline: for each process whose intake takes the email, its title with "Start a case from this email" beside it (the page's one solid button while no case is started from the email; afterwards secondary, "Start another case from this email"), then what the whole record lacks as orange marks (or a green line that it has what a case needs), the cases already started as links, and the record's data in a compact table (a value's source named by its part: "the email's text" or the attachment's file).
- **A case's page and the case list** (231). A case's tabs are its process pack's, numbered, on one row however many there are (the package page's three by default); a tab's state after its name is cut with an ellipsis and shown whole in its tooltip. The send, the follow-up and the cost are plain cards (720 px), the events a full-width card: the send card names the way and the output folder (a path in the mono face, a missing folder an amber ◆), its Send button is the view's one solid action while the step waits for it, and each attempt is a compact row with its state mark (handed over green, unknown amber ◆, failed red ■); the follow-up card lists since when it waits and when the follow-up opens (tabular dates), and recording the reply is solid only while the follow-up is the person's turn. The events table leaves out the core's own bookkeeping; a machine's row says "The system" in muted text. A closed case's header has no next step. The case list ("Cases" in the side rail) shows what a case waits for as a state mark (a person's turn orange, the reply a grey ring, the machine blue, a failed step red ■) and, above the cases only while there are some, the handovers to check.
- **Partners** (231, Settings › Partners). One row of tools: a search field, a role filter, "Retired ones too", and "New partner" (the view's one solid button while no partner is open; secondary once one is). The list is a compact table: the name as a link-like button in ink at 500, the roles in words, the tax number in the mono face (a code), the email, the last change in tabular figures; a retired one carries the retired mark (a dash). A partner opens below the list as a full-width card: its values in the shared form fields, its roles as checkboxes, a note; "Save as a new version" is solid only while something changed and a name and a role are given; Retire asks once more; a conflict names the other partner with "Open it". Its versions follow as a compact table with the shared version marks. The proposals from the documents read load only on request (they read every invoice) and are recorded by a person. On a case's page the partner card names each role's partner (linked: a green mark), or what the record gives with "It seems to be … in the partner register" and "Link it", or "Record as a partner" — secondary buttons, as the page's solid action is its next step.
- **Workflows.** A step's state is a state mark: done green, a person's turn (a budget, to-dos, an approval, pairing) orange, failed red, running blue, starting a blue ring, ready a neutral dot, waiting a grey ring; the list draws the chain with the same marks. The step that needs a person first has a firm ink border and holds the view's one solid button; every start button carries its run's cost cap. In the wizard a choice is a selection (ink border, neutral tint), never the accent, and the current step's number is filled with ink. While the wizard is open, its own next step is the solid button and the page's "New workflow" turns secondary.
- **Settings.** The menu on the left marks the current section as a neutral block in ink, as the side rail does, with no side bar and no accent. One density for everyone: there is no density switch. A theme's choice shows a small drawing of the workspace in that theme (the preview tokens keep their values in both themes); the chosen one has an ink border on the neutral tint. Radio buttons and checkboxes are ink. Its save buttons follow the editor rule under Buttons.
- **Products and Tariffs** (231 stage D, D-c6, Settings). Read like a binder kept as a ledger. Products: a segmented control (Products, Rules, Condition documents, each with its count in tabular figures); each list a compact table whose first column is a link-like button in ink at 500 and whose state column is the shared version mark with "version N" in muted text (a newer draft beside it). A thing opens below its list as one full-width card (its title takes the focus and scrolls into view): the version line (mark, who made it and made it active, when), then the activation between two quiet hairlines, then its parts under 13 px semibold headings, then its versions. The activation follows the approval: "What keeps it from being made active" as the shared blocker lines (each problem translated, where it applies first: "rule x@1: row 2: …"), or a green "Nothing keeps it…"; "Make version N active" is the card's one solid button only when nothing keeps it and the person is not the product's maker (then it is a disabled secondary one with the reason beside it); "Retire" is secondary and asks once more. A rule is a decision table: a row number in muted text, the compared facts, then a 3 px double rule (the ledger's total rule) before the outcomes; "any" in the faint colour; a code by its catalogue label, one without a label (an activity code) in the mono face; amounts with their currency in tabular figures, a whole one without decimals ("5 000 000 HUF"). The clause it was read from is a quiet figure under a 1 px hairline indent: "Read from" in muted text, the document, page and clause, the quoted words in ink. A rule opened inside a product's card is a section under a hairline, never a card in the card. A tariff opens as its computation order: numbered steps, each number a 22 px square-cornered mark with an ink border (`.step-no`), the cover modules' table in the first step (rates and minimums on one line), then the factors as compact tables in a grid of at least 260 px columns.
- **Rule proposals** (231 stage D, D-c7g, Settings › Products › Proposals). The start is one card: the document version and the product as the shared pickers, the file with **Browse…**, the proposer as two plain radio buttons (the stand-in first, named free); with GPT, the budgets, and "Propose rules" carries the run's cost cap (`.spend`) and is the card's solid button only when it can start. Runs are a compact table (the proposer "Stand-in (free)" in muted text; a run's state mark). A run opens as a card: its state line (file, proposer, pages read), the pages its marking left out as an amber notice, then its proposals as a compact table with three state marks side by side: the code's check (ready green, numbers to confirm orange, blocked red ■), JEV's mark (supported green, to check an amber ◆, contradicted red ■, not asked a faint ring) and the decision (to decide an ink dot, accepted or corrected green, rejected a dash). A proposal opens below its table as a section under a hairline (never a card in the card): the decision table and the clause as on the Rules page, "What blocks it" as blocker lines, "What to look at" as warning lines, its numbers as a compact table (a number not in the document or read by text recognition in the to-do colour; a code in the mono face, an amount or factor in the language's notation), then the decision between two hairlines: the numbers to confirm as checkboxes, "Accept as a draft rule" the one solid button only when nothing blocks and every number is confirmed, a rejection's reason with a secondary "Reject" that asks once more, and the correction as a record in the code face folded away.
- **An assessment's data check** (231 stage D, D-f4; the insurance quote's Data check tab). One full-width card read as a ledger. Its head names the state as a mark (to settle orange with the count, to freeze orange, frozen green with the version). What the sources disagree on comes first, as the view's to-do: a 13 px semibold heading in the to-do colour and a compact table (the unit, the fact, the value now, the step that offered the other value, the offered value) with a secondary "Take this value" per row, and one muted line that the system never chooses. Then the units ledger: one table, a unit's head row on the soft tint in ink at 600 (its level in muted text, its name), indented by its depth in the tree, with a quiet "Edit"; its facts under it, the fact's title, the value in ink at 500 (a code by its catalogue label, a code without one in the mono face, an amount with its currency in tabular figures) and the source in muted 12 px text (the file, the page, the quoted words; "register" for a register's answer). Editing turns the unit's facts into the shared inputs (a select for a coded fact or a yes/no, an amount or quantity with its unit beside it); its save follows the editor rule. Facts not placed are amber warning lines. The freeze closes the card under a quiet hairline: the day cover starts, and "Freeze the facts", the view's one solid button only once nothing is to settle and the day is given (otherwise a disabled secondary one with the reason beside it in the to-do colour or muted). A frozen check is a green notice with its version, who, when and the day cover starts, and a secondary "Reopen the check" that takes a reason. The facts read from the documents and a register's answer are plain cards below: a compact table of the documents (a document no reading takes says so in muted text; what was not read is an amber warning line with the fact's title, the words and why), and a register's card with its state mark (answered green, not found or not asked a grey ring, no answer red ■), its description in muted text, what it was asked with and the facts it offers.
- **An assessment's calculation** (231 stage D, D-f5; the insurance quote's Calculation and versions tab). Three cards in the case's order. The rules' evaluation (full width): its verdict as the head's mark (allowed green, to refer orange, refused red ■, not known an amber ◆, blocked red ■), one muted line naming its version, the checked input's version it was made from and the modules evaluated; the facts it missed as to-do lines naming the unit; its blockers as blocker lines; then a compact table of the units in their tree (the level in muted 12 px text above the unit's own name, indented by depth), each unit's outcomes as a short list (the outcome's title in muted text, the value in ink: a code by its label, an amount with its currency) and the rules that gave them (a rule left undecided says so in the to-do colour with the facts it lacks). The wait for missing facts (a plain card): its state mark, each missing fact named with its unit in the to-do colour while the task is open, the deadline in one sentence with what to do, the closing in muted text, and "The facts will not come", a secondary button that takes a reason first. The premium (full width): its total as the head's mark (green) or blocked, one muted line naming its version, the evaluation's version and the tariff; the lines as a compact table grouped by module (the module named on its first line, the unit's own name, the basis, the base premium, the factors as "title ×factor", the amount; every amount on one line in tabular figures), each module's total as a row in ink at 500 under a hairline (its minimum noted in muted text); the factors on the whole as one small line; then the total as the ledger's sum: a 3 px double rule in ink, "Premium" and the 22 px semibold figure on the right. The earlier versions of the evaluation and of the premium are a quiet fold under each ("Earlier versions (n)"), a compact table of version, what it was made from, its outcome and when.
- **A case's decision** (231 stage D, D-f6; the insurance quote's Decision and release tab). A plain card per decision, in the case's order. Its head names the state as a mark (decided green with its choice, to decide orange, returned orange, out of date an amber ◆, waiting a grey ring). "Decides on" names the step and its result in ink at 600 (a verdict in words, a premium in tabular figures). Above a limit, an orange notice says that another person decides, naming the earlier decision's maker; below it, a muted line that anyone may. A decision that holds is a green notice with the choice, who and when, its note in muted text after a dash. While it waits, the choices are plain ink radio buttons under a quiet hairline (one the result does not allow is muted and cannot be taken, with why; one that closes the case says so in muted text), a note (a required reason for a closing choice), and "Record the decision", the card's one solid button only when a choice is taken, its reason given where needed and the person may decide (otherwise a disabled secondary one with the reason beside it in the to-do colour or muted); returning it takes a reason, as the approval's return does. The earlier decisions are a quiet fold.
- **A case's printed document** (231 stage D, D-f7; the insurance quote's Decision and release tab, below the decisions). A plain card: its head names the state as a mark (printed green with the version, waiting a grey ring, not printed red). Printed, a key-value list: the file name as the one link (it downloads the stored file), "Printed from" with the version and the decision it printed, and the fingerprint's first twelve characters in IBM Plex Mono at the small size, the whole one in its tooltip; a muted line under it says the download never changes. Waiting, one muted line names the decision it waits for; a step that could not print it shows a red notice pointing to the step's note.
- **Rules** (218, Settings). Read only, so the page has no solid button. A short introduction, a quiet line linking the price lists and the output templates, which a person edits, then one table: a decision per row, never taller than four lines (its title in ink at 600, the first two lines of what it decides in muted text; its values and its rule files clamped to four lines, the whole text in the tooltip; a threshold's label reads on into its value, as in "below 60 %", with the sign kept beside its number). The title is a link-like button that opens the whole rule below the table (it scrolls into view and its title takes the focus): what it decides, "Not for" in muted text, the values as a ledger of two columns (the condition in secondary ink, the value in ink at 500, tabular; an intent's next steps as a list), the rule files with their code name in the mono face, version, date and since when they are in use here, and the count of decisions in one sentence. The open title is underlined.
- **Output templates** (179, Settings). The upload is one card whose "Upload and check" is the page's one solid button, disabled until a name and a path are given; the output picker's label is drawn like the field labels beside it. A refused file lists each problem as a red ✕ line: the cell in the mono face, the problem in words, an unknown marker in the mono face with its reason in words. Each output's name heads its part, and its templates are one table with the same columns in every part: a version's state is a state mark (active ● green, a draft ○ ink ring, superseded ○ faint ring, retired a dash); a check's warnings are an amber ◆ that opens. The markers are a scrolling table in groups (the values, then each table with its row count and months); a marker is a code in the mono face with a quiet copy button.
- **Template chooser** (179). Beside a download that can have an own template (the full Excel package, the utility cost's workbook, the reconciliation's draft): a quiet "Template" label and a compact picker, the built-in template first. It shows only when an own template can be chosen, so a package without one looks as before; the chooser and its download stay together at the row's end, and on the result row the result picker narrows a little so the row fits 1366 px. A choice retired since is an amber ◆ that says the built-in template is used.
- **Native view** (a Word, Excel, text or CSV document). A location is a quiet code label in the mono face; the selected element has an ink frame; a nested table and a quoted source are indented with a hairline, never a thick side stripe.
- **Small text and figures.** `<small>` is 12 px like `.small` (the browser's own “smaller” gave 10.8 px). A date or an amount outside a table cell takes `.tnum` (tabular figures in the text face), never `.mono`.
- **Links drawn as buttons** (`a.primary`, `a.secondary`) keep the button's look: no underline, and no accent text on hover.
- **Confidence colours on the page image.** Confident green, to check orange (a person's to-do), likely wrong red, entered by a person blue, unknown grey. The scanned page stays white paper in the dark theme too, so its frames keep the light-theme values there.
- **Where a style lives** (195). A page's own stylesheet (`reconcile.css`, `parties.css`, `native.css`) loads with the page, since the rarely used pages load on first use; a class two kinds of page share (the stacked cards `.rc-stack`, the period fields `.rc-period`) belongs in `ui/src/styles.css`, at its end when it used to follow a page's rules, so that the order of the rules stays as it was.

## 5. Tables

- The header may wrap onto two lines; the filter icon floats over the header's corner and appears on hover, on focus and while a filter is active.
- A date-time is drawn as its date and its time, so a narrow column puts the time under the date; its text stays one value.
- Words wrap at spaces; only a name-like column may break inside a long unbroken value (a name, a file name, a path, an e-mail address). The dataset marks such columns (`wrap: "anywhere"`, by key in `jav/app/datasets.py`), so one long address cannot widen a whole table.
- A column whose values can run long may limit its cells to a number of lines (`clamp`, set by the dataset); the full value is the cell's tooltip. The facts table limits its document column to 2 lines, its source to 3 and its value to 4, so no row is taller than 4 lines (183).
- A dataset can give its own columns a minimum width (`.dt-table[data-dataset="…"] th[data-col="…"]`). The work package list's default columns fit 1440 px and 1366 px without sideways scrolling.
- A width a person dragged is kept per browser; the column menu resets it.

## 6. Checking a screen

Before a changed screen is accepted: screenshots before and after in light and dark at 1366 × 768 and 1440 × 900; no sideways scrolling of the page or of a default table; no cell taller than four lines on default columns; no text below 12 px, no colour outside the tokens, no side stripe; the UI tests, the typecheck and the translation check pass.
