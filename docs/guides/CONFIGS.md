# Configuration files

**In force:** since 2026-09-30 (v1.0.5). **Audience:** developers, and users who configure the system.

## Plain-language summary

Every tunable part of the system lives in a configuration file, not in the program code: the descriptions of document types and email intents, the questions put to the AI models, the decision thresholds, the models and their prices, the recipes' budgets and the limits of the local service. Every file has a version number and a changelog, and a fingerprint computed from its content goes into the call-log row of every paid call, so any measurement can be traced back to the settings it ran with. When a question or description sent to a model changes, the next measurement goes through paid calls again, so a sub-budget has to be approved first; thresholds, limits, budgets and switching on a new flow are the owner's decision. The running local service and the worker read the configuration only when they start, so they must be restarted after a change.

## 1. Common rules

A configuration file puts the "config as data" principle into practice ([glossary](../GLOSSARY.md)): the program is the mechanism, the file holds the parameters. Changing a setting is therefore a matter of editing a file and measuring, not of programming, and every change leaves a trace.

1. **Format.** JSON, UTF-8, LF line endings (written from Python with `encoding="utf-8"`). Every file starts with a `meta` block: `name`, `version` (three parts, for example `1.4.0`) and `changelog` (entries with `version`, `date` and `note`). The loader (`jav/core/cfg.py`) rejects a file without a version.
2. **Fingerprint (`config_hash`, "hash" from here on).** The hash is a shortened sha256 of the file's content (16 hex digits). The changelog is not part of it, so a note does not change it; the version number is part of it. The hash goes into the call-log row of every JEV and GPT call made by the flows, together with all the configuration inputs of that call: the call site, the registry or type pack, and the pack's instruction and schema files.
3. **When re-measuring costs money.** The JEV cache key is made up of the exact model version, the state sent and the questions; the hash is not part of it. Any change to a question, the instruction, the glossary or the description of an option (`what` / `not_for` / `examples`) therefore produces a new key, and the next golden run goes through live, paid calls. A bare version bump, or a change to a label or a threshold, does not trigger new calls (OCR is the exception, see section 3). GPT extraction has no response cache, so every run of the G path is paid.
4. **How a content change is made** (CLAUDE.md §4):
   - bump `meta.version` (by convention the third number for a fix and the second for an extension), and append a `changelog` entry that names the round and the reason; the first number only when older content no longer fits the code: a process case keeps the rule files its steps read as it started (231, D0-e), reads a kept file of the same first number as it was (with a key added since from the first later version that had it: a later change of its value does not reach it), and stops a step on one of another first number (`python -m jav.cli cases-kept` lists the open cases it would stop). So a new key that changes the business meaning (a surcharge, a rate, a limit an old case must not take) bumps the first number, and a new technical key with a neutral default bumps the second;
   - run the affected tests;
   - if text sent to the model has changed, do a golden run on the affected flow;
   - run `python -m jav.cli docs` to regenerate the call-site catalogue (local, not in the repository) and the flow descriptions;
   - restart the local service and the worker (section 3).

   A live, paid measurement may only start with a pre-approved sub-budget, on a clean working tree, with the commit hash recorded.
5. **The owner decides** (CLAUDE.md §1 and §2) on thresholds and routes, the set of types and intents (type boundaries), budgets, the limits of the local service, and switching on a new flow or a paid step. The decision is recorded with its date. The "Decision needed?" column in section 2 shows this for each file.
6. **Personal data** must not go into a configuration file either; examples must use made-up values. If a made-up tax number or bank account number happens to have valid check digits, the value must be added to the data guard's exception list ([development workflow](DEVELOPMENT.md), section 1).

## 3. When a change takes effect

The local service and the worker read each configuration file once, when it is first used, and keep it in memory until the process ends; they do not re-read it while running. Command-line commands see the current state every time they start.

| Where | When it sees the change |
|---|---|
| Local service and worker | After a restart (`.\scripts\dev.ps1 stop`, then `start`). |
| A run that has already started | The recipe and the budget are fixed when the run starts (configuration snapshot), so a recipe change does not affect it. The worker read the type pack, the questions and the thresholds when it started, and keeps working with those. |
| UI | `field_labels.json`, `intents.json` and `email_tasks.json` are built into the UI: `cd ui; npm run build`, then reload the browser. |
| Command line (golden, `configs`, `backup`) | Immediately, every time it starts. |
| Data guard (git hooks) | At the next commit or push. |
| Daily backup | The backup starts as a new process every day and reads the `backup` section itself. Only a change of the **time** requires the task to be reinstalled: `.\scripts\backup-task.ps1 install`. |
| OCR cache | The key covers only the `ocr.json` settings that can change the recognised text (`jav/documents/ocr.py` `output_settings`), plus the engine's version line; paths, time limits, notes and the version record do not count. A change to such a setting sends every document through OCR again; with escalation switched on, this can also mean paid Azure pages. The Azure API version is part of Azure's engine version, so changing it re-reads only the Azure texts. |

## 4. Call sites (`configs/callsites/`)

A call site ([glossary](../GLOSSARY.md)) is a point in a flow where JEV is asked a question. Its file holds everything the model sees of the question: the English instruction and glossary, the descriptions of the options, the yes/no questions, the template of the presence question, the number of lines that go into the state, and the request-size budget. Any textual change to the file therefore produces a new cache key: the next golden run and every new run go through live, paid calls. The rules for writing these files are in the [JEV playbook](../JEV_PLAYBOOK.md) and in the JEV checklist of CLAUDE.md.

| File | What it asks | Read by | Measurement after a change |
|---|---|---|---|
| `detect.json` | Broad document type (Choice over the registry), whether the issuer is Hungarian, language (M1) | `jav/ai/detect.py` (hash together with the registry) | `detect-golden`, `detect-determinism` |
| `detect_detail.json` | The detailed type within the broad category, when the anchor score does not decide; the options are the type packs' descriptions | `jav/ai/detect_detail.py` (hash together with all type packs) | `detect-golden` |
| `email_intent.json` | Email intent (Choice), signals (Noul), urgency (Score), injected instruction (M3) | `jav/domains/email/intent.py` (hash together with the intent registry) | `email-golden`, `email-determinism`, `email-injection-probe` |
| `select.json`, `select_foreign.json`, `select_invoice_out.json`, `select_utility.json` | S path: a choice per field among the code's candidates, with a presence question, grouped into requests | `jav/ai/jev_select.py` (hash together with the type pack) | `golden --arm S --type <key>`; before that, the free `recall` |
| `quote_match.json` | Which item of the seller's price list a requested item of a quote request is (191): `item`, a Choice over the list's items (name, code, unit, group; no price) plus none; `listed`, whether the list sells such a thing at all; `specific`, whether the request says enough to tell one item; the state's limits (`max_text_chars`, `max_options`: code keeps the items sharing most words from a longer list) and the candidates a mark to check names (`candidates`). The marks (sure, to check, not listed) use the default policy bands (`quote.match`); code takes an item code written in the request first. | `jav/domains/quotes/quote_match.py` (GPT gets the same texts with `gpt_quote_match.json`) | `measure quote:matches` (free from earlier answers), then with the owner's sub-budget |
| `rule_proposal.json` | 231 (stage D, D-c7d): how far the page a proposed rule was read from supports it: `kind`, a Choice over the rule kinds (each with what it is and is not for) plus none (no rule decidable when making an offer); `row_<n>`, a Noul per row of the decision table, whether the page states that its conditions lead to its results; `left_out`, a Noul, whether the page names something the rule leaves out. The state is the cited page verbatim, the quote and the rule written out by code in English. A mark beside the proposal on the default bands, never an acceptance; skipped without JEV (the code's checks and a person decide) | `jav/app/rule_support.py` | the rule proposal measurement (stage D-h) |
| `reconcile_line.json` | Pre-matching of one statement line of a reconciliation package (134): which of the invoices code preselected it pays, or none (Choice; each option carries the amount and timing facts code computed), and what kind of payment it is (Choice); the preselection (`preselect`: line states, amount share, most options), the kinds that suggest a needs-no-invoice reason (`kind_marks`) and those that expect an invoice (`kind_expects_invoice`); 158 (1.2.0): incoming money has its own kind question (`credit_kind`: a customer's payment, an own transfer, income, interest, a refund, an owner's contribution, other), and the lines code left out for a reason in `preselect.excluded_reasons` are asked the kind only | `jav/domains/finance/reconcile_ai.py` (GPT gets the same texts with `gpt_reconcile.json`) | `reconcile-ai <package>` (free estimate), then with the owner's sub-budget |
| `verify.json`, `verify_<key>.json` | G path: error flags (Noul) on the fields of the GPT extraction | `jav/ai/jev_verify.py` (hash together with the type pack) | `golden --arm G --type <key>`, `verifier-probe` |

- The `select_callsite` and `verify_callsite` fields of a type pack name the call sites it uses.
- 202: an S call site states its document description (`document`), the request each extra question belongs to (`request`) and, per request, the lines it takes besides its candidates' (`extra_lines`: `top_fraction`, `bottom_lines`; `payment_method_lines`). Nothing is inferred from a request's name, so a new type's S call site is configuration only.
- A `verify_<key>.json` inherits the shared error questions through `"inherits": "verify"`, and mainly adds the type's field descriptions (`field_specs`), glossary and request-size budget. The verification call sites of the types taken over from the legacy project were built this way (`jav/legacy/typepack_convert.py`).
- 190: a verification call site names its document-level questions (`document_nouls`; 202: `verify.json` states the three invoice questions - swapped parties, missing and extra line items - and its document description, which every other call site inherits unless it names its own; a call site without them is refused) and the questions asked of each list field of the pack (`list_nouls`, each sent with the list's name as `list_field`; none without the key). A question named there needs its text under `nouls`. A call site that does not inherit `verify` writes its own question texts, so a document that is not an invoice is not asked about an invoice's parties. A pack's `source_prefix` names the words before the source text in the GPT request (without it: the invoice PDF's).
- `request_char_budget` and `option_context_max` make up the request-size budget ([glossary](../GLOSSARY.md)): for an oversized request, the code trims first the text, then the descriptions, and finally the number of candidates.

## 5. Type packs (`configs/types/`)

A type pack ([glossary](../GLOSSARY.md)) holds all the type-specific data needed to extract data from one document type. It states which fields exist and of what kind, which of them are required, high-stakes or informational only, which checks run, which path the extraction takes, and which question set it uses. The extraction flow is type-independent, so a new type needs a new pack, not new code, as long as the existing field kinds are enough. The loader (`jav/ai/typepack.py`) checks the kinds and the field names in the lists, and raises an error on a mismatch.

| Key | Role |
|---|---|
| `document`, `parent`, `detect`, `auto_detect` | Description (also one of the options of the detailed-type question); broad category from the registry; the keywords of the anchor score (`required_any`, `supporting`, `excluders`); whether the type takes part in automatic detailed detection (199: turned by `type-activate` / `type-withdraw`, see the step list below) |
| `fields`, `list_fields`, `enums` | Field → field kind; the columns of line lists; the enumerated values |
| `scored_fields`, `informational_fields`, `required`, `high_stakes` | Scored, informational-only, required and high-stakes fields; these determine the band check and which fields get presence questions |
| `required_review` | 192: `false` turns a missing required field into a note (an advisory check, shown but opening no to-do) instead of the `llm:required_missing` to-do; for a type read as one part of a larger whole judged elsewhere. Only the quote request (its parts are judged on the whole request by its quote package; the owner's decision) sets it, with its list checks advisory too; the default `true` is every other pack's behaviour. It changes no request sent to a model. |
| `validators`, `text_labels` | Code checks (`"review": false` = flag-only check; `distinct_parties` takes two role fields in `fields` and opens a to-do at the second when both name one party; `party_orientation`, in the same shape, opens one when the pair stands the other way round than on most earlier documents of the same type, in worker runs only; 190: a list field's rows by the list's name: `{"check": "list_rows", "field": <list>, "min": 1}` (at least that many rows), `list_values` (the `columns` have a value in every row), `list_positive` (the `columns` are above zero), each a to-do at the list field with its rows named); the labels of free-text fields |
| `candidate_profile`, `arms`, `default_arm` | Candidate profile (`hu`, `intl`, `utility`); the paths the pack can run; the recommended path |
| `plain_list_items` | 190: a list of plain values in the schema (`"items": {"type": "string"}`) becomes a list of such values in the G path's output model; without it (every pack before 190, the default) it is a list of empty objects GPT cannot fill. Turning it on changes the pack's GPT request: with its paid golden run |
| `inputs` | What the pack reads (190): `pdf` (the default; every pack before 190), `text` (an email's own text or a `.txt` file), `table` (an `.xlsx` or `.csv` file, opened by the isolated native reader). A text or table is laid out by the PDF reader's line and cell builder (`jav/documents/text_document.py`), so the extraction sees it like a PDF's lines; it has no word layer |
| `select_callsite`, `verify_callsite` | The names of the two call sites (for a pack without an S path, the first is `null`) |
| `prompt_file`, `schema_file` | The G path's instruction and output schema under `configs/prompts/`; the pack's hash covers their content too |
| `prompt_note` | Optional: instructions added after the prompt file on the G path, so a variant pack reuses another pack's verbatim prompt (the pro forma invoice reuses the Hungarian invoice's) or corrects it without editing the verbatim legacy copy (the tax certificate's employer) |
| `golden_type_key`, `extends` | The golden set's type name in the legacy project; the name of the inherited base pack |
| `legacy_transforms` | The legacy project's transformation rules, recorded by the one-off converter for reference; the runtime does not read them |

**Inheritance.** With `extends`, a pack inherits a base pack from `configs/types/_base/` ([glossary](../GLOSSARY.md): base pack). The base's fields, lists, checks and schema are placed before the child's; today the common part of Hungarian utility bills is such a base. A base pack cannot run on its own and is not in the `configs` list, but the child's hash covers it.

**Instructions and output schemas** (`configs/prompts/`; until 209 `jav/prompts/`). The G path's instruction (`<key>_prompt.md`) and output schema (`<key>_schema.json`) of every pack, and the task proposal's instruction (`email_tasks_prompt.md`, named by `email_tasks.json`). Most are the legacy project's files verbatim; an instruction's leading HTML comment is a header that is cut off on loading (`jav/core/config.py` `load_prompt`). They have no `meta` block and are not in the `configs` list: the hash of the pack or file that names them covers their content, so a changed byte changes that hash, and a changed instruction or schema is text sent to the model (a new cache key and a paid golden run).

**After a change:** `golden --arm S|G --type <key>` where a golden set exists (the types taken over from the legacy project only have synthetic samples); for the S path, the free `recall` first. The description and the field lists also go into the question, so changing them may produce a new cache key.

**Adding a new type** (there is no separate guide yet):

1. pack: `configs/types/<key>.json`, with a `meta` block, and `extends` if needed;
2. instruction and schema: `configs/prompts/<key>_prompt.md` and `<key>_schema.json`;
3. verification call site: `configs/callsites/verify_<key>.json` (`"inherits": "verify"`), and a selection call site too for the S path;
4. a Hungarian name for every field and list column in `field_labels.json` (`tests/test_field_labels.py` flags any that are missing);
5. inventory: `doc_types.json` → `old_type_map` and `capability_catalog.json` → `expected_document_keys`, otherwise the inventory check fails;
6. tests with synthetic data only, then `python -m jav.cli docs`;
7. until the owner has decided on the type boundary, `"auto_detect": false`, so the type does not take part in automatic detection.

**Turning detection on or off** (199): `python -m jav.cli type-activate <key> [--replace <pack>]` and `type-withdraw <key> [--restore]` (`jav/evals/type_teaching.py`). Each switch writes the pack's next version (`auto_detect`, a changelog line; a taught pack's `meta.taught`: its state `candidate` / `active` / `withdrawn`, the measurement it was turned on with and the pack it `replaces`), in the pack's own layout; a refusal writes nothing. A taught pack is turned on only with the latest shared measurement of its evaluation half (`measure taught:<key>:evaluation`) on a clean working tree, every case answered, on the files it has now; a pack that was never taught is turned back on without one. A category's own pack (its detection is the registry's) and a pack read by code only are not switched, and a pack without `detect` anchors only as its family's one pack. The switch changes no extraction or verification request; the family's detailed-type question offers the packs that are on, so a new pack there is a new question (paid). After it: `python -m jav.cli docs`, the family's golden runs, and a restart of the service and the worker.

## 6. Experiments (`configs/experiments/`)

The synthetic cases of the injected-instruction probe (`document_injection.json`); the other September trial settings were removed with their experiments in 204. Neither the `configs` list nor the shared hash covers the folder; the probe records its own source fingerprints in the raw run. Only the probe (`jav/evals/document_injection_probe.py`) reads it; the local service and the worker do not. Changing it therefore has no effect on work-package runs. A paid trial needs a pre-approved sub-budget (some files also set their own cost cap, for example `budget_usd`), and case descriptions may only use synthetic or anonymised data.

## 7. Legacy type copies (`configs/legacy_types/`)

A verbatim copy, per type, of the legacy project's type folders: schema, instruction, rules, detection keywords and the old descriptor. Alongside them is a `manifest.json` with the source path and the sha256 of every file. Some folders also contain `fixtures/synth_*.json`; these are purely synthetic samples. They are read by:

- `jav/legacy/legacy_packs.py`: checks the fingerprints on loading and raises an error on a mismatch;
- `jav/devtools/capability_catalog.py`: coverage;
- `jav/legacy/typepack_convert.py`: the one-off converter that built the corresponding type packs and verification call sites from them.

These files are not edited, because they are source copies. Behaviour is changed in the type pack or call site built from them. They have no `meta` block, they are not in the `configs` list, and automatic routing is switched off for them (`automatic_routing_enabled: false`).

## 8. Checks

- `python -m jav.cli configs`: the name, version, hash and latest changelog entry of every top-level file, call site and type pack. Look up versions and hashes there; this guide deliberately does not list them. `python -m jav.cli admin` shows the same together with the models and prices, and the generated state snapshot (local, not in the repository) contains it too.
- `python -m jav.cli preflight`: its configuration line lists the same. Load errors (invalid JSON, a missing version) show up here and in the tests.
- Tests: `tests/test_cfg.py` (every file loads, the version has three parts, the changelog is not empty, the hash is stable and unaffected by the changelog), `tests/test_field_labels.py`, `tests/test_capability_catalog.py`, `tests/test_recipe_help.py`, `tests/test_encoding_guard.py` (accented text written back with the wrong encoding), `tests/test_docs_071.py` (this guide names every `configs/*.json` file).
- When a new top-level configuration file is added, `tests/test_docs_071.py` fails until this guide names it; its row in the section 2 table still has to be written by hand.
